A model is only "good" relative to something

R² — compared to what?

You fit a line. It makes predictions. "The errors are small" isn't a number you can compare across models — you need an actual baseline to measure against.

The simplest possible baseline

"If I knew nothing about x at all, my best guess for every single y would just be the average — ȳ. Any real model, using real information from x, should beat that."
R² measures exactly how much better than that "just guess the mean" baseline your model actually is.
The mechanics

R² — the formula

R2 = 1 − SSres / SStot

SSres — unexplained

nΣi=1(yi − ŷi)2

Your model's own squared errors — this is just SSE, from Lecture 2.

SStot — total

nΣi=1(yi − ȳ)2

The baseline's squared errors — always predicting the mean. Unnormalized variance.

R² = 1 → perfect fit  ·  R² = 0 → exactly as good as guessing the mean  ·  R² < 0 → worse than guessing the mean

Testing on data the model already saw proves nothing

Train-test split

If you fit on every row you have, then check error on those same rows, you're measuring memorization, not generalization.

Training set

What the model learns from — every weight comes only from these rows.

Test set

Held back, untouched during fitting — used only afterward to check real performance.

In code — predicting selling price

from sklearn.model_selection import train_test_split X = data.drop(columns='selling_price') # features y = data['selling_price'] # target X_train, X_test, y_train, y_test = train_test_split( X, y, test_size=0.2, random_state=10 )
80% trains the model, 20% is held back purely to grade it afterward — untouched during fitting.
Is it actually random?

random_state, explained

Yes, by default — until you fix the seed. Then it's "the same randomness every time," not "no randomness."

Without a fixed seed

train_test_split(X, y, test_size=0.2) # run 1: rows [3, 17, 42, ...] end up in test # run 2: rows [8, 21, 55, ...] end up in test — different!

Two runs, two different splits, two slightly different trained models, two different scores. Not reproducible.

random_state=10 fixes this

It's a seed number — any integer works, 10 is just this notebook's choice, nothing special about it. The same seed always reproduces the exact same split.

This isn't "no randomness" — it's "the same randomness, every time." The split is still effectively random relative to the data; fixing the seed just makes it repeatable, so results are comparable across runs.

One exception worth knowing

If rows represent a sequence over time, don't shuffle — use shuffle=False and split chronologically instead. Random shuffling would leak the future into training.

The actual ranges these features live in

Why scaling matters

📅

age

Ranges roughly 0–15 years — a total spread of about 15.

🛣️

km_driven

Ranges roughly 5,000–150,000 km — a spread in the hundreds of thousands.

⚙️

engine_cc

Ranges roughly 800–2,500 cc — a spread in the thousands.

What happens with no scaling

Any calculation combining these raw values — comparing coefficients, computing distances, running gradient descent — lets km_driven's sheer numeric size dominate, purely because its units happen to be hundreds of thousands, not tens. The same learning rate that's sensible for age is wildly wrong for km_driven — this is the exact elongated-bowl problem from Lecture 2's gradient descent.

no scaling → unstable gradient steps, and coefficients you can't honestly compare to each other.
Two ways to put every feature on the same footing

Scaling methods

Min-Max scaling

x′ = (x − min) / (max − min)

Forces every value into a fixed 0-to-1 range.

Standard (z-score) scaling

x′ = (x − mean) / std

Recenters to mean 0, rescales to a spread of 1 std deviation.

In code

from sklearn.preprocessing import StandardScaler scaler = StandardScaler() X_train_scaled = scaler.fit_transform(X_train) X_test_scaled = scaler.transform(X_test) # fit on train only — test uses train's mean & std, never its own
Notice: .fit_transform() on train, plain .transform() on test — the scaler learns its mean/std from training data only, exactly like the model itself.
Same model, same data — just rescaled first

Feature importance — after scaling

A coefficient on a standardized feature equals the original coefficient × that feature's own std — because standardizing simply undoes the scale the coefficient was fighting against.
