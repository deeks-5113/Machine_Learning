01 · the bridge

We already know GBDT. So why do we need XGBoost?

Nothing here is a new algorithm family. It is the same idea — sequential trees, each one correcting the current model — made mathematically sharper and practically safer.

Ask yourself: what could go wrong with plain GBDT that a smarter optimisation and some explicit penalties would fix?

What GBDT already does well

  • Sequential correction of residuals — genuinely powerful
  • Works for regression and classification via the loss function
  • Shrinkage (learning rate) already controls step size

Where it is exposed

  • Splits are found the same way as an ordinary regression tree — SSE reduction on the gradient target. Nothing about tree complexity is explicitly penalised.
  • Only the first derivative is used. A leaf value is essentially a mean of gradients — it never asks "how confident is this correction, given the curvature of the loss here?"
  • Nothing stops a leaf weight from swinging large just because a few rows push hard in one direction.
  • No principled, mathematical rule for "is this split even worth it" — depth/leaf-count limits are blunt instruments.

The one-sentence version: XGBoost takes every place where GBDT made an implicit or ad-hoc choice, and replaces it with an explicit term in the objective function — then optimises that objective properly, using both derivatives.
02 · first principles

What exactly is XGBoost optimising?

Start from the model itself — a sum of trees.

\[ \hat y_i=\sum_{k=1}^{K}f_k(x_i) \]
SymbolMeaning
\(\hat y_i\)final prediction for row \(i\)
\(f_k\)the \(k\)-th tree — a function mapping features to a leaf value
\(K\)total number of trees
Additive model: each tree adds its own correction on top of everything built so far. Nothing here is new — this is exactly \(F_m=F_{m-1}+\eta f_m\) from GBDT, just written as one sum.
The full objective

Every model needs something to minimise. XGBoost's objective has two parts — not one:

\[ Obj=\sum_{i=1}^{n}l(y_i,\hat y_i)+\sum_{k=1}^{K}\Omega(f_k) \]
TermMeaning
\(\sum_i l(y_i,\hat y_i)\)training loss — how wrong are the predictions (this is all GBDT optimises)
\(\sum_k \Omega(f_k)\)a complexity penalty on every tree — this is the genuinely new piece

And \(\Omega\) itself is defined as:

\[ \Omega(f)=\gamma T+\frac12\lambda\sum_{j=1}^{T}w_j^2+\alpha\sum_{j=1}^{T}|w_j| \]
SymbolMeaning
\(T\)number of leaves in the tree
\(w_j\)the value (weight) of leaf \(j\)
\(\gamma\)flat penalty per leaf — punishes having too many leaves
\(\lambda\)L2 penalty on leaf weights — punishes large weights, squared
\(\alpha\)L1 penalty on leaf weights — punishes large weights, in absolute value
Do not just say "regularisation prevents overfitting." Be precise about what is being punished: \(\gamma\) punishes having more leaves at all; \(\lambda\) punishes a leaf's weight being large (smoothly); \(\alpha\) punishes a leaf's weight being large too, but in a way that can push it all the way to exactly zero.

03 · second-order optimisation

Why Taylor expansion? And what is it, really?

At round \(t\), we want to add a new tree \(f_t\) to minimise:

\[ Obj^{(t)}=\sum_i l\big(y_i,\hat y_i^{(t-1)}+f_t(x_i)\big)+\Omega(f_t) \]
Ask yourself: \(f_t\) is a whole tree, not a number. Why can't we just directly minimise this?

Because \(l\) can be any loss (squared error, log loss, ...) with \(f_t(x_i)\) buried inside it in a way that has no clean, general closed-form minimum. We need a way to approximate the loss near the current prediction that is simple enough to actually optimise — a quadratic. That's exactly what Taylor expansion gives us.

What is Taylor expansion, from a single number

Take any smooth function \(f(x)\). Near a point \(x\), moving by a small step \(\Delta\):

\[ \text{first-order: }\quad f(x+\Delta)\approx f(x)+f'(x)\Delta \]

This is just "the tangent line" — use the slope at \(x\) to guess the value a little further along. Add one more term and you get the tangent parabola instead of a line:

\[ \text{second-order: }\quad f(x+\Delta)\approx f(x)+f'(x)\Delta+\frac12f''(x)\Delta^2 \]

First derivative \(f'(x)\)

Local slope. "Which way, and how steeply, does the function change?"

Second derivative \(f''(x)\)

Local curvature. "How quickly does that slope itself change?" A flat, wide bowl vs a narrow, sharp bowl have very different \(f''\).

Why curvature matters here: the slope alone tells you a direction to move. The curvature tells you how far you can trust that direction before the approximation breaks down — a sharply curving loss needs a smaller, more careful step than a gently curving one.
Now map this directly onto XGBoost

Our "function of \(\Delta\)" is the loss, our "current point" is the current prediction \(\hat y_i^{(t-1)}\), and our "step" is the new tree's output \(f_t(x_i)\). Define:

\[ g_i=\frac{\partial l(y_i,\hat y_i)}{\partial \hat y_i}\bigg|_{\hat y_i=\hat y_i^{(t-1)}},\qquad h_i=\frac{\partial^2 l(y_i,\hat y_i)}{\partial \hat y_i^2}\bigg|_{\hat y_i=\hat y_i^{(t-1)}} \]

Then the second-order Taylor approximation of the loss for row \(i\) is:

\[ \boxed{l\big(y_i,\hat y_i^{(t-1)}+f_t(x_i)\big)\approx l(y_i,\hat y_i^{(t-1)})+g_i f_t(x_i)+\frac12h_i f_t(x_i)^2} \]
Be exact about what is being differentiated. \(y_i\) (the actual label) is treated as a fixed constant. We differentiate the loss with respect to the current prediction \(\hat y_i\) — asking "if my prediction nudges slightly, how does the loss respond?" That is the only variable in play.
04 · the crucial bridge

Is \(g_i\) something completely different from the GBDT pseudo-residual?

Ask yourself: we already learned pseudo-residuals in GBDT. Is XGBoost throwing that away and starting over?

No. Watch what happens for squared-error loss.

\[ l(y_i,\hat y_i)=\frac12(y_i-\hat y_i)^2 \]

Differentiate with respect to \(\hat y_i\):

\[ g_i=\frac{\partial l}{\partial \hat y_i}=\hat y_i-y_i \]
\[ h_i=\frac{\partial^2 l}{\partial \hat y_i^2}=1 \]
So \(g_i\) is exactly the negative of GBDT's residual. GBDT's pseudo-residual is \(r_i=y_i-\hat y_i\). XGBoost's gradient is \(g_i=\hat y_i-y_i=-r_i\). Same information, opposite sign convention (because XGBoost's update adds \(w\) directly, rather than adding "the residual").
XGBoost is not magic. It generalises the exact same idea GBDT already taught you — "fit the tree to how wrong the current model is" — but does it with both derivatives instead of just the first, and folds in explicit regularisation. Every \(g_i,h_i\) formula from here on is just this same differentiation, applied to a different loss.

Ask yourself: not "the mean" by assumption — derive it. What constant \(c\) minimises the total loss before any tree exists?
\[ \hat y^{(0)}=\arg\min_c\sum_i\frac12(y_i-c)^2 \]

Differentiate with respect to \(c\) and set to zero:

\[ \frac{d}{dc}\sum_i\frac12(y_i-c)^2=\sum_i(c-y_i)=0\ \Rightarrow\ c=\frac{\sum_i y_i}{n} \]
\[ \boxed{\hat y^{(0)}=\bar y=\frac{2+4+6+8+10+12}{6}=7} \]
The mean isn't chosen by convention. It falls straight out of minimising squared-error loss with no tree yet. \(F_0=7\) for every row.

Do not jump straight to "the answer" split. The tree has to actually try every candidate threshold and score each one. That's next — but first, given a chosen region, what's its optimal value?
Derive the regularised leaf weight, from scratch

For any single leaf receiving rows with gradient sum \(G\) and Hessian sum \(H\), the (second-order-approximated, regularised) objective contributed by that leaf is:

\[ Obj_{\text{leaf}}(w)=Gw+\frac12(H+\lambda)w^2 \]

Differentiate with respect to \(w\) and set to zero:

\[ \frac{\partial\, Obj_{\text{leaf}}}{\partial w}=G+(H+\lambda)w=0 \]
\[ \boxed{w^*=-\frac{G}{H+\lambda}} \]
Intuition: \(G\) says which way to correct and how hard. \(H+\lambda\) is the "resistance" — more curvature (more confident rows) OR more L2 penalty both make the leaf more reluctant to move far. Set \(\lambda=0\) and this is exactly GBDT's second-order form \(-G/H\).
07 · regression, worked end-to-end

Split gain: derived from scratch, not just stated

The tree does not simply "split on the residual mean." It must score every candidate threshold. Substitute the optimal \(w^*\) back into the leaf objective:

\[ Obj_{\text{leaf}}(w^*)=G\left(-\frac{G}{H+\lambda}\right)+\frac12(H+\lambda)\left(\frac{G^2}{(H+\lambda)^2}\right) =-\frac{G^2}{H+\lambda}+\frac12\frac{G^2}{H+\lambda} \]
\[ \boxed{Obj_{\text{leaf}}(w^*)=-\frac12\frac{G^2}{H+\lambda}} \]

A split replaces one parent leaf with two child leaves. It is worth doing only if the total objective drops:

\[ \text{drop}=Obj_{\text{parent}}-\big(Obj_{\text{left}}+Obj_{\text{right}}\big) =\left(-\frac12\frac{G^2}{H+\lambda}\right)-\left(-\frac12\frac{G_L^2}{H_L+\lambda}-\frac12\frac{G_R^2}{H_R+\lambda}\right) \]

Rearranged, and after subtracting the flat per-leaf cost \(\gamma\) of creating one extra leaf:

\[ \boxed{Gain=\frac12\left(\frac{G_L^2}{H_L+\lambda}+\frac{G_R^2}{H_R+\lambda}-\frac{G^2}{H+\lambda}\right)-\gamma} \]
Positive gain = the two specialised leaves genuinely reduce the objective more than the flat cost of creating them. Negative gain = not worth splitting; that region becomes a leaf as-is.

10 · regression, worked end-to-end

Learning rate, mathematically

\[ F_t(x)=F_{t-1}(x)+\eta\, f_t(x) \]
ηEffect
1.0Full correction applied immediately. Fast, but the model can overshoot — each tree is trusted completely, including its noise.
0.5Half the correction. Faster than small η, still fairly aggressive.
0.1Small, careful steps. Needs many more trees to reach the same place, but each tree's error contributes less.
0.01Very conservative. Excellent generalisation potential, but needs a large \(n\_estimators\) and more training time.
The core trade-off: large \(\eta\) → fast but unstable, prone to overfitting individual trees' noise. Small \(\eta\) → slow but controlled, usually paired with more trees and early stopping.
Ask yourself: if η is tiny, is more trees always better? No — past a point validation loss plateaus or worsens even with small steps, which is exactly why early stopping exists (covered later).

Regression: what exactly changed from GBDT?

GBDTGBDT

Pseudo-residual → regression tree fit by SSE → leaf = mean residual

XGBoostXGB

Gradient + Hessian → regularised objective → tree split by \(G,H\)-Gain → regularised leaf weight

\[ w_{\text{GBDT}}\sim-\frac{G}{H}\qquad\text{vs}\qquad w_{\text{XGB}}=-\frac{G}{H+\lambda} \]
For squared error, \(H=1\) per row always — so GBDT's leaf value collapses to the plain mean residual. XGBoost's \(+\lambda\) in the denominator is the only new thing here: it shrinks the leaf weight toward zero, proportionally more so with fewer/lower-confidence rows in the leaf.
12 · classification, from first principles

What changes when y is binary?

Ask yourself: regression was fairly direct — the tree corrects a real number. What does the tree correct when the target is 0/1?

Start from binary log loss:

\[ l(y,p)=-\big[y\log p+(1-y)\log(1-p)\big] \]

XGBoost's tree does not directly predict a probability. It works with a raw score (margin) \(F(x)\), converted to a probability via the sigmoid:

\[ p=\sigma(F)=\frac{1}{1+e^{-F}} \]
Every tree adds a correction to \(F\), the unbounded raw score — never directly to \(p\), which is squeezed into \([0,1]\) and behaves badly under simple addition. This is identical to how GBDT classification worked; nothing new here yet.

14 · classification, worked end-to-end

Derive \(g\) and \(h\) for log loss, step by step

Gradient
\[ l(y,F)=-y\log p-(1-y)\log(1-p),\qquad p=\sigma(F) \]

Using \(\dfrac{d\sigma}{dF}=\sigma(F)(1-\sigma(F))=p(1-p)\) and the chain rule:

\[ \frac{\partial l}{\partial F}=\frac{\partial l}{\partial p}\cdot\frac{\partial p}{\partial F} =\left(-\frac{y}{p}+\frac{1-y}{1-p}\right)\cdot p(1-p)=p-y \]
\[ \boxed{g_i=p_i-y_i} \]
Hessian

Differentiate \(g=p-y\) with respect to \(F\) again, using the same \(\frac{dp}{dF}=p(1-p)\):

\[ \frac{\partial^2 l}{\partial F^2}=\frac{\partial}{\partial F}(p-y)=\frac{dp}{dF}=p(1-p) \]
\[ \boxed{h_i=p_i(1-p_i)} \]

Gradient \(p-y\)

"How wrong is the current probability?" Positive when we're over-predicting the positive class, negative when under-predicting.

Hessian \(p(1-p)\)

"How much curvature does log loss have here?" Maximal at \(p=0.5\) (most uncertain, most room to move), shrinks toward 0 as \(p\to0\) or \(p\to1\) (already confident, loss is flat).

16 · regularisation, deep

L1: why would we punish |w|?

Ask yourself: why punish the absolute value of a leaf weight, rather than just leaving it alone?

Because it lets a leaf's contribution be pushed all the way to exactly zero — effectively "switching that leaf off" — something a smooth penalty like L2 cannot do. A zero-weight leaf contributes nothing to the prediction, as if that region of the tree didn't exist.

Why L1 needs special handling: \(|w|\) is not differentiable at \(w=0\) (there's a corner, not a smooth curve), so we can't just set a derivative to zero the usual way. The fix is soft-thresholding.
Soft-thresholding, derived

Minimising \(Gw+\frac12(H+\lambda)w^2+\alpha|w|\) piecewise (for \(w>0\) and \(w<0\) separately, since \(|w|\) is smooth on each side) gives:

\[ \text{Threshold}(G,\alpha)= \begin{cases} G-\alpha & G>\alpha\\ 0 & |G|\le\alpha\\ G+\alpha & G<-\alpha \end{cases} \]
\[ \boxed{w^*=-\frac{\text{Threshold}(G,\alpha)}{H+\lambda}} \]
If \(G\) isn't strong enough to overcome the penalty \(\alpha\), the optimal weight is exactly 0. Only a gradient signal that clears the \(\alpha\) bar survives, and even then it's reduced by \(\alpha\) before being scaled.

Numeric example — G=3, H=4, λ=1

17 · regularisation, deep

L2: shrink, don't zero out

Ask yourself: why square the weight instead of using its absolute value?

Squaring makes the penalty smooth everywhere (differentiable at \(w=0\), no corner) and makes large weights disproportionately expensive — doubling \(w\) quadruples its penalty. This is exactly the \(-G/(H+\lambda)\) we already derived.

λw* = -G/(H+λ), G=3,H=4Effect
0-0.750no shrinkage — matches GBDT's second-order form
1-0.600mild shrinkage toward 0
5-0.333strong shrinkage, weight compressed but never exactly 0
L2 never produces an exact zero — it keeps shrinking the weight as \(\lambda\) grows, but the weight only approaches zero asymptotically. Contrast this directly with L1's hard zero above.
18 · regularisation, deep

γ: the price of a new leaf

Ask yourself: what does XGBoost actually punish with γT?

The number of leaves — a flat cost charged per leaf, completely independent of how good or bad that leaf's correction is. It shows up directly inside Gain:

\[ Gain=\text{(improvement from split)}-\gamma \]

Revisit the regression iteration-1 candidate table with a strict \(\gamma=25\):

SplitRaw improvementGain (−25)Split?
x≤3.5 (best)20.25-4.75No — stays a single leaf
Even the best possible split (20.25) can't clear a γ of 25. The whole region collapses into one leaf. This is exactly how γ makes a tree "more conservative about creating new leaves" — not by limiting depth directly, but by demanding every split earn its keep.

20 · practical machinery

min_child_weight: not "minimum sample count"

Common misconception: it is not simply "each child needs at least N rows." It is a constraint on \(\sum h_i\) — the total Hessian mass in a child.

For squared-error regression, \(h_i=1\) always, so \(\sum h_i\) literally equals the row count — min_child_weight does behave like a row-count minimum there. But for classification, \(h_i=p_i(1-p_i)\) varies per row: confident rows (\(p\) near 0 or 1) contribute almost no Hessian mass, while uncertain rows (\(p\) near 0.5) contribute the most.

A child made of 50 confident, easy rows might have less total Hessian than a child made of 5 genuinely uncertain rows. min_child_weight is really asking: "is there enough real, curvature-weighted evidence here to trust this split?"
min_child_weightEffect
tiny (near 0)almost any split allowed, even on a couple of uncertain rows — high overfitting risk
moderaterequires meaningful accumulated evidence per child — typical default territory
very largeonly very well-supported splits survive — tree stays shallow, risk of underfitting

Recall the λ=1,γ=0 regression split at \(x\le3.5\): \(H_L=H_R=3\). With min_child_weight=5, that split would be rejected — neither child clears the bar.

→
Keep whichever direction wins
store as default
During training, missing rows for a given feature are excluded from the split-threshold search, then tried entirely on the left and entirely on the right — whichever gives higher Gain is stored as that node's "default direction." During prediction, any row missing that feature is sent straight down the stored default direction, no re-computation needed.
This is very different from mean/median imputation. XGBoost never guesses a value — it learns, per split, which side missing rows behave more like.
22 · practical machinery

Histogram-based splitting: why, and how — precisely

Ask yourself: a feature has 10,000 unique values. Checking every possible threshold for every split, on every tree, is exactly how expensive?

Extremely. Exact greedy search sorts the feature and evaluates a candidate at every distinct value — correct, but \(O(n)\) candidates per feature, per split, per tree, repeated across every tree in the ensemble.

Continuous feature
→
Bin into a histogram
e.g. max_bin=256
→
Aggregate G,H per bin
→
Evaluate split between bins
not between raw values
→
Choose best gain
Step 1 — how are the bin boundaries even chosen?
Not equal-width, and not simple equal-row-count either. XGBoost builds bins using a weighted quantile sketch: boundaries are placed so each bin holds roughly equal total Hessian mass (\(\sum h\)), not an equal number of rows.

Why weight by \(h\) and not just count rows? Because \(h\) is literally "how much this row's loss curves here" — how much it matters to get this region right. A cluster of confident, low-\(h\) classification rows (near \(p{=}0\) or \(p{=}1\)) can be lumped into one coarse bin cheaply; a cluster of uncertain, high-\(h\) rows (near \(p{=}0.5\), where the split actually matters) gets finer bin resolution automatically.

Step 2 — a genuinely small worked example (12 rows → 4 bins)

12 sorted rows of a feature "age", with each row's \(g_i\) (say \(h_i=1\) for simplicity, i.e. squared-error regression):

age121518222529333844516072
g-3-2-2-1-10011223

Exact greedy would check 11 candidate thresholds here (between every consecutive pair). With \(\text{max\_bin}=4\), the rows are grouped into 4 bins first (roughly equal Hessian mass — here, equal count since every \(h_i=1\)):

BinAges insideG (sum g)H (sum h)
112, 15, 18-73
222, 25, 29-23
333, 38, 4423
451, 60, 7273
Notice: 12 unique values collapsed into just 4 aggregated buckets. Any two rows landing in the same bin (e.g. age 12 and age 18) are now indistinguishable to the split-finder — a split can never separate them within this round. That's the entire approximation, in one sentence.
Step 3 — "all combinations" is NOT what happens; it's a single left-to-right pass
There is no combinatorial search over which bins go left vs right. With 4 bins there are technically \(2^3=8\) ways to 2-partition them, but XGBoost never explores that space. Because the feature is sorted, a valid split must always be a contiguous prefix vs suffix of bins — so it only ever needs the 3 boundaries between consecutive bins (\(\text{bins}-1\) candidates), found with one cumulative left-to-right sweep, exactly like exact greedy, just running on 4 aggregated buckets instead of 12 raw rows.
Candidate (boundary after)GL,HLGR,HRGain (λ=1,γ=0)
Bin 1 | Bins 2-4  (age≤~20)-7, 37, 98.58
Bins 1-2 | Bins 3-4  (age≤~31)-9, 69, 611.57
Bins 1-3 | Bin 4  (age≤~47)-7, 97, 38.58
Exactly 3 candidates evaluated (not 11, and nowhere near \(2^3\)) — one cumulative pass through the sorted bins, accumulating \(G,H\) left-to-right, scoring the boundary after each bin. This is precisely the same prefix-sum mechanic as exact greedy's candidate-threshold table earlier in these notes — just computed on 4 compressed buckets instead of 12 raw rows.
Big picture: with 10,000 unique values and \(\text{max\_bin}=256\), the same logic gives at most 255 candidate boundaries to check — a linear scan over bins, never a search over raw values, and never combinatorial. The actual split threshold ultimately reported is a bin edge (e.g. "age ≤ 31.4"), not one of the original 10,000 exact values.

25 · tuning

Underfitting vs overfitting, through the objective

Underfitting

Training AND validation both poor — the model lacks capacity, or is over-constrained.

  • learning_rate too small + too few trees
  • max_depth too low
  • min_child_weight too high
  • gamma too high
  • reg_alpha / reg_lambda too high
  • subsample / colsample too low

Overfitting

Training keeps improving, validation worsens or plateaus — the ensemble is memorising specifics.

  • too many trees, no early stopping
  • learning_rate too high
  • max_depth too high
  • min_child_weight too low
  • gamma too low
  • regularisation too weak overall
  • subsample / colsample too high (no stochastic dampening)
Do not just minimise training loss. Every one of these knobs is really a knob on the objective's complexity term — the goal is the best trade-off between fitting the data and staying simple enough to generalise.

Hyperparameters don't act alone

PairInteraction
learning_rate ↔ n_estimatorsSmall η usually needs proportionally more trees to reach the same fit — tune together, not independently.
max_depth ↔ min_child_weightDepth controls how far a tree can grow; min_child_weight controls whether each individual split has enough Hessian mass to be trusted. A deep tree with a high min_child_weight often can't actually reach its max depth.
gamma ↔ max_depthBoth limit complexity, but differently — gamma demands a split "earn its keep" via Gain; max_depth is a hard structural ceiling regardless of Gain.
reg_lambda ↔ leaf weightDirectly inside \(w^*=-G/(H+\lambda)\) — raising λ shrinks every leaf weight, interacting with how aggressive splits even look during Gain comparison.
reg_alpha ↔ leaf sparsityHigher α means more leaves get zeroed via soft-thresholding — effectively pruning the tree's influence without changing its structure.
subsample ↔ colsample_*Both add stochasticity from different axes (rows vs columns). Pushing both very low at once can starve individual trees of enough signal — tune jointly, watch validation closely.

28 · tuning

Class imbalance: scale_pos_weight, from first principles

With heavy imbalance (say 99% negative, 1% positive), the model can achieve very low average loss just by always predicting "negative" — the rare positive rows barely move the aggregate gradient.

\[ g_i^{\text{weighted}}=w_i\,(p_i-y_i),\qquad w_i=\text{scale\_pos\_weight if }y_i=1\text{ else }1 \]
Multiplying positive-class gradients (and Hessians) by scale_pos_weight makes each positive row "count for more" in every \(G,H\) sum — directly changing which splits look good and how large leaf weights become, forcing the model to pay real attention to the minority class instead of ignoring it.

A common heuristic is \(\text{scale\_pos\_weight}=\dfrac{\#\text{negative}}{\#\text{positive}}\) — but treat it as a starting point, not a law; validate against your actual metric (often recall/precision/F1/AUC rather than accuracy) and against your chosen decision threshold.

29 · tuning

Feature importance: weight vs gain vs cover

MethodMeasuresReads as
weightnumber of times a feature is used to split, across all trees"how often was this feature picked at all"
gainaverage Gain improvement from splits using this feature"how much did this feature actually improve the objective, on average"
coveraverage \(\sum h\) (Hessian mass) of rows affected by splits on this feature"how much curvature-weighted data did this feature typically influence"
Gain is usually the most informative: a feature used only once but responsible for a huge loss reduction (high gain, low weight) is often more valuable than one split on constantly but each time only marginally useful (high weight, low gain).
Feature importance is not causal importance. It reflects how useful a feature was for reducing loss inside this particular model, given every other feature it competed with and correlated against — not a claim about real-world cause and effect.
30 · final algorithm

XGBoost, end-to-end without skipping steps

Regression

1
Initialise: \(\hat y^{(0)}=\bar y\), the constant that minimises squared loss.
2
Compute: \(g_i=\hat y_i-y_i\), \(h_i=1\), for every row.
3
Build candidate splits: every threshold on every feature.
4
Aggregate: \(G_L,H_L,G_R,H_R\) for each candidate.
5
Regularised Gain: \(\frac12\big(\frac{G_L^2}{H_L+\lambda}+\frac{G_R^2}{H_R+\lambda}-\frac{G^2}{H+\lambda}\big)-\gamma\), pick the best; reject if best Gain ≤ 0.
6
Leaf weight: \(w_j^*=-G_j/(H_j+\lambda)\) (soft-thresholded first if \(\alpha>0\)).
7
Update: \(\hat y_i^{(t)}=\hat y_i^{(t-1)}+\eta\, w_j\).
8
Repeat from step 2 with the new predictions; stop via n_estimators or early stopping.

Binary classification

1
Initialise: \(p_0=\bar y\), \(F_0=\log[p_0/(1-p_0)]\).
2
Probability: \(p_i=\sigma(F_i)\).
3
Compute: \(g_i=p_i-y_i\), \(h_i=p_i(1-p_i)\).
4
Candidate splits, aggregate G,H, regularised Gain — identical machinery to regression, on this round's g,h.
5
Leaf weight: \(w_j^*=-G_j/(H_j+\lambda)\).
6
Update raw score: \(F_i^{(t)}=F_i^{(t-1)}+\eta\, w_j\), then recompute \(p_i=\sigma(F_i)\).
7
Repeat from step 3; stop via n_estimators or early stopping.

Equations worth remembering
\[\boxed{g_i=\hat y_i-y_i,\quad h_i=1}\ \text{(regression)}\]
\[\boxed{p_i=\sigma(F_i),\quad g_i=p_i-y_i,\quad h_i=p_i(1-p_i)}\ \text{(classification)}\]
\[\boxed{w^*=-\frac{\text{Threshold}(G,\alpha)}{H+\lambda}}\ \text{(with L1)}\]
\[\boxed{Gain=\frac12\left(\frac{G_L^2}{H_L+\lambda}+\frac{G_R^2}{H_R+\lambda}-\frac{G^2}{H+\lambda}\right)-\gamma}\]
\[\boxed{Obj=\sum_i l(y_i,\hat y_i)+\gamma T+\frac12\lambda\sum_j w_j^2+\alpha\sum_j|w_j|}\]

The one-sentence mental model

XGBoost repeatedly builds a tree using both the direction (\(g\)) and the confidence (\(h\)) of the current error, scores every candidate split with a regularised Gain that has to earn its keep, assigns each leaf a shrunk-and-possibly-zeroed correction, applies it cautiously via η, and repeats.
