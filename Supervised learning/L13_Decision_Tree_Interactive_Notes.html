The problem

Why Not Logistic Regression, or KNN?

Employee attrition data, 2 features: Age and OverTime. Plot it first.

× = employees who left. ● = employees who stayed.

Will Logistic Regression work?

No. Logistic Regression is a linear model — it can only draw ONE straight boundary. Look at the plot: the "Leave" region is boxed in on two sides (young AND high overtime). No single straight line can carve out that box. Logistic Regression will underperform here, structurally.

Will KNN work?

It could classify this correctly — KNN doesn't need a straight boundary, and this data satisfies KNN's core assumption (similar points cluster together). But it can't be productionized well. Every single prediction requires comparing the new employee against ALL stored training employees — O(n·d) per prediction. At real HR-system scale (thousands of employees, checked constantly), that's too slow.
We need something that handles non-linear regions like Logistic Regression can't, AND predicts fast like KNN can't. That's a Decision Tree.
The core idea

See It, Then Write If-Else

Two straight cuts (one vertical on Age, one horizontal only within the left region) perfectly separate Leave from Stay.
if Age < 30:
    if OverTime >= 2.5:
        predict # Leave
    else:
        predict # Stay
else:
    predict # Stay

The exact same logic, drawn as a tree

How Do We Automate This?

Manually writing if-else per feature does NOT scale. With 2 features and 12 rows, we can eyeball it. Real data has dozens of features and millions of rows — nobody is hand-drawing boundaries on a 40-dimensional scatter plot.
We need 2 things: (1) a feature to split on, and (2) a condition to split it by — and we need to LEARN both automatically from the data, at every single node. That's what "training" means for a decision tree. Everything from here on is the math that makes this automatic.
Entropy & Gini

Entropy, Explained

Entropy measures how "mixed up" (impure) a node is. A node with only one class: entropy = 0 (totally predictable). A node split evenly between classes: entropy = maximum (a coin flip).

H(y) = − Σ p(yi) · log2( p(yi) )

A jar-of-balls intuition, in 3 steps

JarContentsConfidence picking Red?Entropy
Jar 13 Red, 3 BlueTotal guess1.00 (max)
Jar 25 Red, 1 BluePretty confident0.65
Jar 36 Red, 0 BlueCertain0.00 (min)
Entropy is maximum when a node is impure (50/50), minimum (0) when pure, and always lies between 0 and 1 for a binary target.

Gini — The Faster Alternative

The problem with entropy

Entropy needs a log₂ computation, for every feature, at every node, for every candidate split, across the whole tree-building process. That's a LOT of logarithms on real data.

The fix: Gini Impurity

GI(y) = 1 − Σ p(yi)²

Same idea — 0 when pure, maximum when evenly split — but only needs squaring and subtraction. No logarithms anywhere.

Try it in the playground above — switch the metric dropdown between Entropy and Gini for the same class counts. They rank splits almost identically; Gini is just cheaper to compute. This is why sklearn's DecisionTreeClassifier defaults to Gini.
Information Gain

Level 1: Age<35 vs Gender

100 employees, 60 Stay / 40 Leave. Two candidate features to split the root on: Age<35, or Gender. Which one actually helps more?

Information Gain = H(parent) − Weighted Average of H(children)

Candidate A — Age < 35

1 Parent entropy = 0.971
2 Left (Yes, n=60): H=0.650    Right (No, n=40): H=0.811
3 Weighted children = 0.6×0.650 + 0.4×0.811 = 0.7145
IG = 0.971 − 0.7145 = 0.257

Candidate B — Gender

1 Parent entropy = 0.971
2 Male (n=70): H=0.863    Female (n=30): H=0.918
3 Weighted children = 0.7×0.863 + 0.3×0.918 = 0.8797
IG = 0.971 − 0.8797 = 0.091
Age<35 wins clearly (IG=0.257 vs 0.091) — the root splits on Age<35.

Level 2: Splitting Again, Inside Age<35

The Age<35 branch (60 Stay, 10 Leave, H=0.650) still isn't pure. Compare two NEW candidate features for splitting it further: OverTime≥2.5, or Gender.

Candidate A — OverTime ≥ 2.5

1 Parent entropy = 0.650
2 Yes (n=15): H=0.918    No (n=45): H=0.000 (pure!)
3 Weighted children = 0.25×0.918 + 0.75×0.000 = 0.230
IG = 0.650 − 0.230 = 0.420

Candidate B — Gender

1 Parent entropy = 0.650
2 Male (n=40): H=0.310    Female (n=20): H=0.881
3 Weighted children = 0.667×0.310 + 0.333×0.881 = 0.500
IG = 0.650 − 0.500 = 0.150
OverTime≥2.5 wins even more decisively here (IG=0.420 vs 0.150) — and the "No" child is already perfectly pure (H=0.000, all 45 stayed). That branch stops; only the "Yes" side (n=15) needs further splitting.

A doubt worth addressing directly: can the SAME feature come back at a later level?

Yes — absolutely, and it happens all the time. A tree never "uses up" a feature after one split. At every node, ALL features (including ones already used higher up) are tried again, with a fresh search over thresholds. If a feature still separates that specific node's data well, it wins again — possibly with a completely different threshold.

Concretely: take the OverTime≥2.5 "Yes" branch above (n=15: 5 Stay, 10 Leave, H=0.918). Age can legally be tried here again — not with the old cutoff of 35, but searched fresh:

1 Try Age < 25 (a brand-new threshold, not 35): Left (n=8: 1 Stay, 7 Leave) H=0.544, Right (n=7: 4 Stay, 3 Leave) H=0.985
2 Weighted children = (8/15)×0.544 + (7/15)×0.985 = 0.750
IG = 0.918 − 0.750 = 0.169    (a genuinely positive, usable gain)
Age shows up twice in this tree — once as Age<35 at the root, and again as Age<25 several levels deeper — each time chosen fresh because it happened to give the best Information Gain at that specific node, not because of any memory of its earlier use.
The whole algorithm in miniature: at every single node, try every candidate feature (yes, even repeats), compute Information Gain for each, keep the best one, recurse. A real tree just keeps doing this until nodes are pure or a stopping rule kicks in.

Maximum Information Gain Is What We Want

At every node: compute Information Gain for every candidate feature (and every candidate threshold, for numerical features — next section). Pick whichever gives the MAXIMUM Information Gain. That single greedy rule, applied recursively, is the entire decision tree training algorithm.
Numerical features

How Numerical Splits Actually Work

A categorical feature splits cleanly (Male/Female). A numerical feature like Age could split anywhere. sklearn's approach:

1 Sort all n unique values of the feature.
2 Take the midpoint between every pair of consecutive sorted values as a candidate threshold — that's n−1 candidates.
3 Compute Information Gain for EVERY candidate threshold.
4 Keep whichever threshold gives the highest gain.
Example: Age values [17,19,20,25,31,35] → candidate thresholds are the 5 midpoints: 18, 19.5, 22.5, 28, 33. Each one gets its own Information Gain computed, and the best one wins.

Why This Hurts at Scale

Recall the build-time formula: O(n · log(n) · f) — n=samples, f=features. That's because sorting n values costs O(n log n), and we repeat that sort for every one of the f features, at every node. Let's watch that formula predict real, measured time as BOTH n and f grow together.

Read the last row plainly: 100,000 rows × 100 numerical features takes almost 1.8 SECONDS just to build one tree. The formula column and the actual-time column grow together at nearly the same rate all the way down the table — that's the proof that O(n·log(n)·f) isn't just theoretical, it's exactly what you feel as a real wait time. Double the features, and you roughly double the wait. Double the samples, and the wait grows slightly faster than double (because of the log(n) term).
Practical fixes: bin numerical features into a handful of ranges first (fewer candidate thresholds to search per feature), cap max_depth (fewer nodes total need this search repeated), or use max_features so not every feature is evaluated at every single node.
Overfitting

Depth=1 vs Unlimited Depth

A deliberately harder dataset this time: two features X1, X2, where the TRUE rule is a checkerboard — Class 1 if (X1<5 AND X2<5) OR (X1≥5 AND X2≥5), Class 0 otherwise. This genuinely needs at least 2 splits to separate at all — a single cut can never do better than a coin flip here, on purpose, so underfitting shows up clearly.

Notice the checkerboard: Class 1 (×) occupies the top-right and bottom-left quadrants, Class 0 occupies the other two. No single straight cut separates this.

The full depth sweep, train vs test

The classic U-shape: both lines rise together while underfitting, then test accuracy peaks and falls while train keeps climbing — that gap IS overfitting.
Both failure modes are now unmistakable: at depth=1, the tree is bad on data it HAS seen and data it HASN'T (56.2% / 45.6%) — it simply doesn't have enough splits to represent a checkerboard. At depth=8+, it's perfect on data it has seen (100%) but measurably worse on new data (85.6%) than the depth=5 tree was — it has started memorizing noise instead of the true pattern.

Other Hyperparameters

HyperparameterWhat it controlsHigher value →Lower value →
max_depthMax levels the tree can growMore overfitting riskMore underfitting risk
min_samples_splitMin points needed to split a node furtherLess overfittingMore overfitting
min_samples_leafMin points a leaf must containLess overfittingMore overfitting
max_leaf_nodesTotal leaf count allowedMore overfitting riskLess overfitting risk
max_featuresHow many features considered per splitMore overfitting riskLess overfitting risk, more randomness
criteriongini (default) or entropyNot an overfitting knob — almost always agree on the best split
Pattern to remember: max_* parameters are ceilings — raising them gives MORE room to overfit. min_* parameters are floors — raising them makes it HARDER to keep splitting, fighting overfitting. Easy to mix up which direction is "safe" across these two groups.
Tune max_depth (or any of these) exactly like K in KNN: sweep several values, measure performance on a validation set at each, pick the value at the peak — never the training set, never a guess.
Regression Trees

MSE Instead of Entropy / Gini

Predicting continuous marks (not Pass/Fail) from StudyHours. Entropy/Gini need class PROBABILITIES — there are none for a continuous target. Swap in Mean Squared Error, and swap "majority vote" for "mean" as the prediction.

MSE(node) = (1/n) Σ (yi − ȳ)²    where ȳ = mean of the node's targets

Seeing the split as a prediction line

Green dots = the 8 real (StudyHours, Marks) points. The blue and red horizontal segments ARE the tree's predictions — a flat line at 47.0 for anyone below the threshold, jumping to a flat line at 80.0 above it. A regression tree's prediction is always a staircase like this, never a smooth slope.
