We ended Class 14 exactly here: a single Decision Tree is unstable, and that instability is precisely what ensembles are built to fix. Today we build that fix properly — Random Forest, end to end — and then circle back to control a single tree's complexity via pruning.

Bagging → Random Forest

What Is Bagging?

Bagging = Bootstrap Aggregating

Two ideas glued together:

Bootstrap

From your original dataset D, create MANY new datasets by resampling — drawing rows WITH replacement, same size as D each time. Each resample is slightly different: some rows appear twice, some don't appear at all.

Aggregating

Train one model on each resampled dataset, then COMBINE their predictions — vote for classification, average for regression.

Bagging is a general recipe — it works with ANY base algorithm (Decision Trees, Logistic Regression, KNN...). Today we bag Decision Trees specifically, which is the first ingredient of Random Forest.

Each Db is a genuinely DIFFERENT training set — different rows, different duplicates, different missing rows. Fitting a Decision Tree on each one, independently, produces THREE structurally different trees, even though they all came from the same original D. This is bagging's entire mechanism: manufacture controlled diversity, then combine.
The rows that never got drawn for a given tree (3,6 for Tree 1; 2,5 for Tree 2; 1,4,8 for Tree 3) are that tree's Out-of-Bag (OOB) rows — we come back to this in a few minutes, because it gives us a free validation signal.

Random Forest = Bagging + Column Subsampling

Bagging alone (Decision Trees as the base learner) already gives you three different trees, as we just saw. Random Forest adds exactly ONE more ingredient on top:

Random Forest = Bagging (bootstrap rows)  +  Random Feature Subsampling (at every split)
Bagging (of trees)Random Forest
Row samplingBootstrap (with replacement)Bootstrap (with replacement) — SAME as bagging
Feature availability per splitALL features always availableOnly a RANDOM SUBSET available, refreshed every split
How different are the trees?Different, but tend to agree at the root (strongest feature usually wins everywhere)MORE different — strongest feature is sometimes unavailable, forcing genuine diversity
Both bootstrap rows AND randomly restrict features. This second ingredient is what today's "column subsampling" section is about — and it's the detail most people get wrong, so we'll be very precise about it below.
Out-of-Bag

What Is an OOB Point?

Look back at D1 = {1,2,2,4,5,5,7,8}. Rows 3 and 6 were never drawn — Tree 1 never trained on them. That's the entire definition:

An OOB (Out-of-Bag) point, for a specific tree, is any row that tree never saw during training — because bootstrap sampling with replacement happened to skip it. It's "out of the bag" of rows that went into building that tree.

Simple visualization — 8 rows × 3 trees

Row 7 was in-bag for ALL three trees — it never got a chance to be "OOB" here (pure chance, common with few trees). Every other row is OOB for at least one tree — that tree can honestly evaluate its prediction on that row, since it never trained on it.

This number was computed WITHOUT holding out a single dedicated validation row. Every one of the 8 rows contributed to training the forest (via whichever trees included it); it was simply never scored by a tree that had already memorized it. That's the entire trick — and it's essentially free.
Feature (Column) Subsampling

Subsampled Per NODE, Not Per Tree

This is the single most misunderstood detail in Random Forest. The wrong mental model: "each tree randomly picks a fixed set of features and uses only those for its whole life." That is NOT what happens.

The correct model: at EVERY single split (every node, in every tree), a FRESH random subset of features is drawn. The same tree can have Age available at the root but NOT available two nodes later — and Age might come back again at a deeper node. Nothing is fixed for "the whole tree."

Concrete setup

p = 6 features: Age, Income, Balance, Tenure, Transactions, CreditScore     mtry = 2

At every node, only 2 of the 6 features are randomly drawn as candidates. Watch how this plays out inside ONE tree:

Income never won a single split in this whole tree, despite being a candidate once — but it might dominate a DIFFERENT tree entirely, where the random draw happened to favor it more. Averaged across hundreds of trees, every feature gets a fair, repeated chance to prove itself, at many different nodes, under many different candidate combinations.

Why Random Forest?

The Instability of a Single Decision Tree

Two training sets differing by exactly ONE row. Dataset A has (Age=31, Income=50K, Default=N). Dataset B has that same row changed to Default=Y.

Tree fit on A: root split Age < 30      Tree fit on B: root split Age < 33

Evaluate both trees at a NEW test point, Age=31:

Tree A: 31 ≥ 30 ⇒ right ⇒ predicts N      Tree B: 31 < 33 ⇒ left ⇒ predicts Y
One row out of eight flipped the prediction entirely. Not a fluke — it's structural: the root split is chosen by comparing thresholds on whatever rows happen to be in the training set, and once the root changes, every node beneath it inherits a DIFFERENT subset of rows, so every split below can change too. This is exactly what "high variance" means: VarD[ƒ̂D(x)] is large — the tree's prediction at a fixed point x swings a lot depending on which dataset D trained it.

Why Each Tree SHOULD Be Low Bias, High Variance

The natural instinct: "if instability is the problem, make every tree simple and stable — shallow, restricted, low variance." This is the wrong fix. Here's why.

Imagine 100 students given a genuinely hard problem. Force every student to use the same simplified, "safe" reasoning, and they ALL make the SAME mistake. Instead, let each student explore deeply and form their own detailed interpretation. Some will make mistakes — but if their mistakes are DIFFERENT from each other, the group's consensus becomes far more reliable than any "safe but shallow" approach ever could be.
Design choiceBiasVariance (single tree)Forest result after averaging
Deep, unrestricted treesLowHighFalls sharply, IF trees are diverse
Shallow, restricted treesHighLowerStill high bias — averaging can't fix systematic mistakes
Random Forest is excellent at reducing variance. It does not fix bias. If every tree is wrong in the same systematic way, averaging just gives you the same wrong answer with more confidence. Deep trees start with the easy problem (variance, fixable by averaging) instead of the hard one (bias, not fixable by averaging) — that's the whole justification for deliberately keeping individual trees expressive.

Why Trees Must NOT Be Correlated

Suppose every tree in the forest IS deep and expressive (low bias) — is that alone enough? Only if they're also sufficiently DIFFERENT from each other.

If T1(x) = T2(x) = ... = TB(x) (identical trees), then averaging gives back the SAME T(x)
100 identical trees = effectively ONE tree. If all trees make correlated errors — say they all overpredict together whenever a certain pattern appears — averaging them does NOT cancel that shared error out. The forest inherits the correlated mistake at full strength.

The Variance Formula, With Correlation

End-to-end derivation optional — the full step-by-step algebraic derivation (starting from Var(a+b), building up to B trees, proving every assumption) is in the companion PDF on the drive: "Why Random Forest Reduces Variance." Here we go straight to the result and build intuition with numbers.
Var(Random Forest) = ρσ² + (1−ρ)σ²/B
SymbolMeaning
σ²Variance of ONE single tree's prediction, on its own
ρAverage correlation between any two trees' predictions
BNumber of trees in the forest

Three scenarios, B=100 trees, σ²=1

ρ=0 (independent)

Var(RF) = 0 + 1×1/100 = 0.01

99% variance reduction — the ideal case.

ρ=0.9 (highly correlated)

Var(RF) = 0.9 + 0.1/100 = 0.901

Barely better than ONE tree — 100 trees wasted.

ρ=1 (identical)

Var(RF) = 1 + 0 = 1.000

Exactly a single tree's variance. Zero benefit.

Correlation dominates. More trees (bigger B) barely helps once ρ is high — the curve is almost flat near ρ=1 regardless of B.
This is exactly why Random Forest bothers with column subsampling at all. Bootstrap rows alone lowers ρ only a little — if one feature is by far the strongest predictor, nearly every bootstrapped tree will still find it and put it at the root, keeping trees correlated. Randomly hiding features at each split forces genuinely different trees to emerge, pushing ρ down — which the graph above shows is the single biggest lever on the whole formula.
Pruning

What Is Pruning, and Why?

Pruning = deliberately REMOVING parts of a tree to control its complexity

A fully-grown Decision Tree keeps splitting until it nearly memorizes the training data — training error approaches 0, but test error starts rising past a certain depth (classic overfitting, from Class 13). Pruning is the tool that fixes this for a SINGLE tree.

Note the contrast with today's earlier sections: inside a Random Forest we deliberately let trees stay deep and unpruned (ensemble averaging handles their variance). Pruning matters most when you have one single tree and no ensemble to average its instability away.

Pre-Pruning

Pre-pruning = stop the tree from growing too much, WHILE it's being built

Already familiar from Class 13/14 — a handful of intuitive stopping rules, checked at every node BEFORE deciding whether to split further:

ParameterWhat it controls
max_depthMaximum levels the tree may reach
min_samples_splitMinimum rows required to even attempt a split
min_samples_leafMinimum rows required in each resulting leaf
max_leaf_nodesTotal leaf budget for the whole tree
Cheap, easy to tune — but GREEDY. A split that looks weak right now might have led to a genuinely useful split one level deeper; pre-pruning never lets the tree grow far enough to find out.

Alpha — the hyperparameter that controls how much gets pruned

Rα(T) = R(T) + α·|T|

R(T) = the tree's error. |T| = number of leaves. α = price charged PER leaf. This single number is the dial that decides how aggressively to prune:

α valueWhat happensResult
α = 0No penalty for extra leaves at allFull, unpruned tree survives → OVERFITTING
α smallWeak penaltyOnly clearly-useless leaves get removed
α "just right"Balances error vs complexityBest validation performance — the goal
α very largeEvery leaf is extremely expensiveTree collapses toward 1 leaf → UNDERFITTING

Small worked example

A 3-leaf subtree: R(T)=0.1667 (training error). Compare 3 candidate α values:

α=0: Rα = 0.1667 + 0×3 = 0.1667  (full tree wins — nothing to lose by keeping every leaf)
α=0.1: Rα = 0.1667 + 0.1×3 = 0.4667  (now compare against a smaller, 2-leaf alternative...)
α=0.5: Rα = 0.1667 + 0.5×3 = 1.6667  (leaves are now VERY expensive — smaller trees start winning easily)
This is exactly the sweet-spot search: pick a handful of candidate α values, compute Rα for each resulting tree, and let VALIDATION data (not training error) tell you which one actually generalizes best.
Full step-by-step, round-by-round detail in a separate document — the exact weakest-link algorithm (which subtree gets collapsed first, how αt is derived per node, verified against sklearn's cost_complexity_pruning_path(), for both classification AND regression) is worked through completely in the companion notes on the drive: "Post-Pruning, In Full." Go through that for the full round-by-round computation — today's notes give you the concept and the hyperparameter intuition.

For probabilities, predict_proba() on a single tree just reads off the leaf's own class proportions — e.g. a leaf with 8 Yes / 2 No gives P(Yes)=0.8, P(No)=0.2. Still just ONE leaf's opinion, nothing aggregated.

predict() & predict_proba() For Random Forest

The SAME test point now walks through EVERY tree independently — B separate root-to-leaf journeys, B separate opinions, then combined.

P̂(Y=k | x) = (1/B) B∑b=1 I(ŷb = k)
I(·) = 1 if tree b predicted class k, else 0. Averaging these 0/1 votes across all B trees IS the estimated probability for class k.

Worked example — 5 trees, one test point

P̂(Yes) = 3/5 = 0.60     P̂(No) = 2/5 = 0.40
predict() ⇒ Yes (majority)     predict_proba() ⇒ [0.40, 0.60]
Version-specific detail — some RF implementations use a hard 0/1 vote per tree (as shown above); scikit-learn's RandomForestClassifier specifically averages each tree's own predict_proba (its leaf's class proportions) rather than a hard vote by default. Both converge to a similar idea, but the exact numbers can differ slightly — always check your library's docs.

Feature Importance

Recap: Importance For One Tree

Already covered in Class 14 — quick recap of the formula before extending it.

ΔI = I(parent) − [ (nL/n)·I(left) + (nR/n)·I(right) ]
FIj(tree) = ∑nodes splitting on feature j (nnode/ntotal) · ΔInode
Not a usage count. A feature used ONCE at the root (affects 100% of data, big impurity drop) can easily outrank a feature used FIVE times deep in the tree (each time affecting a tiny, already-pure subset).

Extending to the Whole Forest

FIjRF = (1/B) B∑b=1 FIj(b)
Simple average of each tree's own (already normalized to 1) importance vector, across all B trees.

When a Feature Is Missing From a Subtree

Direct consequence of column subsampling: a feature can be COMPLETELY UNAVAILABLE at every node of a given tree, purely by the luck of the random draw — not because it's weak.

If Feature A never gets randomly offered as a candidate anywhere in Tree 3 — or gets offered but never wins — its contribution for Tree 3 is exactly FIA(3) = 0. No hidden default, no imputed value. It just averages in as a zero for that one tree.

Full numerical example — 4 trees, 4 features

Age0.400.100 (never used)0.200.175
Income0.400.350.550 (never used)0.325

Check every column sums to 1.0 first — that's how you know each tree's own importance vector was properly normalized BEFORE averaging: Tree 1 = 0.40+0.40+0.20+0 = 1.00 ✓   Tree 2 = 0.10+0.35+0.30+0.25 = 1.00 ✓   Tree 3 = 0+0.55+0.25+0.20 = 1.00 ✓   Tree 4 = 0.20+0+0.35+0.45 = 1.00 ✓

Income was completely absent from Tree 4 (contributed exactly 0 there) yet still finished with the HIGHEST forest importance (0.325) — because in the three trees where it WAS available, it was extremely useful (0.40, 0.35, 0.55). Being unavailable in one tree — an artifact of random feature subsampling, not a judgment about usefulness — doesn't drag down a feature's overall standing if it earns high importance whenever it IS given the chance.
Never confuse USAGE FREQUENCY ("how often was this feature even offered/selected?") with IMPORTANCE ("how much impurity reduction did it contribute when it won?"). A feature can be rare and powerful, or common and weak — the forest average captures the second thing, not the first.
