Linear Regression

Predict a continuous target by learning a weighted sum of features.

01 · Computation — remember this

Core: ŷ = β₀ + β₁x₁ + … + βₚxₚ
Training: choose β to minimize Σ(yᵢ−ŷᵢ)² (OLS). Closed-form exists conceptually: β=(XᵀX)⁻¹Xᵀy when invertible; practical solvers may use numerical optimization.
Prediction: multiply each feature by its learned coefficient, add intercept.
Remember: linear model = linear in parameters; features can be transformed/polynomial while coefficients remain linear.

02 · Algorithm in one flow

Best when the signal is approximately additive/linear or interpretability matters. Start here as a baseline before complex models.

DATA → PREPROCESS (if needed) → TRAIN / FIT → VALIDATE → TUNE → TEST → DEPLOY / MONITOR

03 · Hyperparameters & effect

• alpha / regularization strength (Ridge/Lasso): ↑ alpha → smaller coefficients → more bias, less variance.
• fit_intercept: whether to learn β₀.
• Ridge: L2 shrinks coefficients; Lasso: L1 can drive coefficients to zero.
• Polynomial degree is a model-complexity knob: ↑ degree → lower bias, higher variance.

04 · Bias ↔ Variance

High bias if relationship is nonlinear; variance is usually lower than flexible models. More features/degree can increase variance. Regularization trades variance for bias.

05 · When to consider

• Strong baseline; roughly linear relationship.
• Need interpretability/coefficient direction.
• Many features and need regularization.
• High-dimensional sparse data → regularized linear models are often strong.
Think twice: strongly nonlinear interactions without useful feature engineering.
Not ideal: severe nonlinear structure that trees/boosting can capture directly.

06 · When NOT to reach for it

  • Don't choose by algorithm popularity; match the data geometry, scale, latency, interpretability and error cost.
  • Always compare against a simple baseline with the metric that reflects the real objective.

07 · Outliers / data issues

• Input outliers: OLS can move coefficients substantially because squared residuals heavily penalize large errors.
• Target outliers: especially influential; can pull the fitted line toward them.
• Consider robust regression, transformations, clipping/winsorization, or investigate data quality.
• Scaling is not required for plain OLS mathematically, but is useful for regularized models and numerical stability.

08 · Classification / multiclass

Regression only. No native multiclass extension needed.

09 · Interview decision cue

Best when the signal is approximately additive/linear or interpretability matters. Start here as a baseline before complex models.

02 / 09

Logistic Regression

A linear classifier that converts a linear score into class probability.

01 · Computation — remember this

Binary: z = β₀ + βᵀx; p(y=1|x)=σ(z)=1/(1+e⁻ᶻ).
Training: minimize log loss (cross-entropy), usually with numerical optimization.
Prediction: probability → threshold (often 0.5, but choose threshold for business cost/recall/precision).
Decision boundary: β₀+βᵀx=0 at p=0.5.
Regularization: penalizes large coefficients and improves generalization.

02 · Algorithm in one flow

Best when the boundary is approximately linear, features are many/sparse, or calibrated-ish probabilities and interpretability matter. Don't force it onto strongly nonlinear feature interactions.

DATA → PREPROCESS (if needed) → TRAIN / FIT → VALIDATE → TUNE → TEST → DEPLOY / MONITOR

03 · Hyperparameters & effect

• C in sklearn: inverse regularization strength. ↑ C → weaker regularization → lower bias, potentially higher variance.
• penalty: L1/L2 (solver-dependent).
• solver: affects optimization and supported penalties.
• class_weight='balanced': useful for class imbalance.
• threshold: changes precision/recall without retraining.

04 · Bias ↔ Variance

Usually higher bias and lower variance than trees/boosting. Regularization ↑ → bias ↑, variance ↓.

05 · When to consider

• Strong baseline for linearly separable-ish problems.
• Excellent when probability estimates + interpretability matter.
• Sparse/high-dimensional text-like features can work very well.
Not ideal: highly nonlinear boundaries unless features/interactions are engineered.
Consider before trees: when you need simple, stable, explainable behavior.

06 · When NOT to reach for it

  • Don't choose by algorithm popularity; match the data geometry, scale, latency, interpretability and error cost.
  • Always compare against a simple baseline with the metric that reflects the real objective.

07 · Outliers / data issues

• Input outliers: can affect coefficients, especially influential points far from the boundary.
• Target outliers are not the regression concept here; mislabeled observations can distort the boundary.
• Scaling is often important, especially with regularization and optimization.
• Severe imbalance: use class weights, suitable threshold, PR-AUC/recall/precision, and careful validation.

08 · Classification / multiclass

• Binary: direct sigmoid model.
• Multiclass: OvR trains one classifier per class, or multinomial/softmax jointly models all classes (solver-dependent).

09 · Interview decision cue

Best when the boundary is approximately linear, features are many/sparse, or calibrated-ish probabilities and interpretability matter. Don't force it onto strongly nonlinear feature interactions.

K-Nearest Neighbors (KNN)

Predict from the labels/values of the most similar training examples.

01 · Computation — remember this

Training: essentially store the training data (lazy learner).
Prediction: 1) compute distance from query to training points → 2) choose k nearest → 3) classification = majority/vote (often distance-weighted); regression = mean/weighted mean.
Distance: Euclidean is common; choice of metric defines “similarity.”
Critical: scaling changes distances, so feature scaling is usually essential.

02 · Algorithm in one flow

Consider for small/medium data, meaningful local neighborhoods, and nonlinear patterns. Avoid when dimensionality is high or inference latency/memory is a concern.

DATA → PREPROCESS (if needed) → TRAIN / FIT → VALIDATE → TUNE → TEST → DEPLOY / MONITOR

03 · Hyperparameters & effect

• n_neighbors (k): ↑ k → smoother boundary, bias ↑, variance ↓. ↓ k → flexible, bias ↓, variance ↑.
• weights: uniform vs distance.
• metric: Euclidean/Manhattan/etc.
• p: distance parameter for Minkowski metrics.
• leaf_size affects tree-backed neighbor search efficiency, not the prediction rule itself.

04 · Bias ↔ Variance

k is the main bias–variance knob. Small k → low bias/high variance. Large k → high bias/low variance.

05 · When to consider

• Useful when local similarity is meaningful and dataset is not huge.
• Can model nonlinear boundaries without explicit fitting.
Not ideal: very high-dimensional data (curse of dimensionality), huge training sets with expensive inference, or poorly scaled/mixed feature spaces.
Think carefully: irrelevant features can destroy distance quality.

06 · When NOT to reach for it

  • Don't choose by algorithm popularity; match the data geometry, scale, latency, interpretability and error cost.
  • Always compare against a simple baseline with the metric that reflects the real objective.

07 · Outliers / data issues

• Input outliers: may become isolated; with small k they can affect nearby predictions. Distance is highly sensitive to extreme feature values.
• Target outliers: in regression, an extreme y can strongly affect the local average; distance weighting can reduce influence if it is not extremely close.
• Scaling is one of the most important preprocessing steps.
• Missing/categorical variables require an appropriate representation/distance.

08 · Classification / multiclass

• Classification naturally supports multiclass via majority vote among all classes.
• Regression predicts a local average, not a class probability unless separately estimated.

09 · Interview decision cue

Consider for small/medium data, meaningful local neighborhoods, and nonlinear patterns. Avoid when dimensionality is high or inference latency/memory is a concern.

Decision Tree

Recursively split the feature space into regions where targets become more homogeneous.

01 · Computation — remember this

Training: at a node → try candidate feature/threshold splits → calculate impurity/loss reduction → choose best split → recurse on children → stop by constraints.
Classification: Gini/entropy-type impurity; leaf predicts class/probability.
Regression: squared-error/MSE-type reduction; leaf predicts a constant (typically mean y in the leaf).
Prediction: follow one path from root to leaf → use leaf prediction.

02 · Algorithm in one flow

Think tree when relationships are nonlinear, interactions matter, feature scales differ, or you want little preprocessing. Regularize or ensemble it rather than using a fully grown tree by default.

DATA → PREPROCESS (if needed) → TRAIN / FIT → VALIDATE → TUNE → TEST → DEPLOY / MONITOR

03 · Hyperparameters & effect

• max_depth: ↑ → complexity ↑, bias ↓, variance ↑.
• min_samples_split / min_samples_leaf: ↑ → simpler tree, bias ↑, variance ↓.
• max_features: fewer features per split → more randomness, usually variance ↓ but bias may ↑.
• criterion: split objective.
• pruning/ccp_alpha: stronger pruning → simpler tree.

04 · Bias ↔ Variance

Deep/unrestricted tree → low bias, high variance. Shallow/pruned tree → higher bias, lower variance.

05 · When to consider

• Great for nonlinearities, thresholds, interactions, mixed feature scales; no scaling required.
• Easy rule-like explanations.
Not ideal: a single unrestricted tree is unstable/high variance and often weaker than ensembles.
Use: interpretable baseline or base learner for ensembles.

06 · When NOT to reach for it

  • Don't choose by algorithm popularity; match the data geometry, scale, latency, interpretability and error cost.
  • Always compare against a simple baseline with the metric that reflects the real objective.

07 · Outliers / data issues

• Input outliers: often less sensitive than distance/linear methods because splits depend on ordering/thresholds; extreme values can still create tiny leaves or affect split choices.
• Target outliers: regression leaf means can be pulled strongly; squared-error splits are sensitive to extreme y.
• Classification label noise can create small pure leaves and overfit.
• Scaling generally unnecessary.

08 · Classification / multiclass

Native multiclass classification: a split separates groups; leaf stores class distribution/probabilities. No OvR required.

09 · Interview decision cue

Think tree when relationships are nonlinear, interactions matter, feature scales differ, or you want little preprocessing. Regularize or ensemble it rather than using a fully grown tree by default.

Random Forest / Bagging

Reduce the variance of decision trees by averaging many randomized trees.

01 · Computation — remember this

Bagging: draw bootstrap samples → train separate base trees independently → aggregate.
Random Forest: additionally randomizes the subset of features considered at each split.
Prediction: classification = vote/average class probabilities; regression = average tree predictions.
Why it works: averaging less-correlated noisy trees reduces variance.

02 · Algorithm in one flow

Consider first for strong, low-maintenance tabular performance, mixed feature scales, nonlinear interactions, and noisy datasets. Consider boosting instead when squeezing out extra accuracy is the priority.

DATA → PREPROCESS (if needed) → TRAIN / FIT → VALIDATE → TUNE → TEST → DEPLOY / MONITOR

03 · Hyperparameters & effect

• n_estimators: ↑ usually stabilizes predictions; compute ↑, variance ↓ until diminishing returns.
• max_depth: deeper trees → lower bias/higher individual-tree variance.
• max_features: smaller → more tree diversity, often variance ↓ but bias can ↑.
• min_samples_leaf/split: ↑ → regularization.
• bootstrap, max_samples: control resampling.
• class_weight: useful for imbalance.

04 · Bias ↔ Variance

Trees have high variance; bagging/RF mainly attacks variance through averaging and decorrelation. Bias is usually not reduced as aggressively as boosting.

05 · When to consider

• Excellent tabular baseline; nonlinearities/interactions with little feature engineering.
• Robust, parallelizable, less tuning-sensitive than boosting.
Not ideal: when maximum predictive performance is needed on structured/tabular data and boosting can be tuned; very large forests can be memory-heavy.
Strong choice: noisy data where variance reduction is valuable.

06 · When NOT to reach for it

  • Don't choose by algorithm popularity; match the data geometry, scale, latency, interpretability and error cost.
  • Always compare against a simple baseline with the metric that reflects the real objective.

07 · Outliers / data issues

• Input outliers: generally more robust than linear/KNN because splits use thresholds; extreme values can still create unusual branches.
• Target outliers: regression averaging can be influenced, though many trees dilute individual effects; squared-error trees remain sensitive.
• Scaling not needed.
• OOB score can estimate generalization when bootstrap sampling is enabled.

08 · Classification / multiclass

Native multiclass: each tree predicts among all classes; aggregate votes/probabilities across trees.

09 · Interview decision cue

Consider first for strong, low-maintenance tabular performance, mixed feature scales, nonlinear interactions, and noisy datasets. Consider boosting instead when squeezing out extra accuracy is the priority.

Gradient Boosting Decision Trees (GBDT)

Build trees sequentially, with each new tree correcting the current model’s errors via the loss gradient.

01 · Computation — remember this

Start: F₀(x) = initial prediction.
For each round m: 1) compute pseudo-residual rᵢ = −∂L(yᵢ,F(xᵢ))/∂F at current F → 2) fit a small regression tree to r → 3) add a shrunken tree update: Fₘ=Fₘ₋₁+η·treeₘ(x).
Key distinction: classical GBDT is fundamentally first-order gradient boosting; tree fitting uses regression-style targets/criteria depending on implementation.
Prediction: sum the initial model + all tree contributions.

02 · Algorithm in one flow

Think GBDT when you want strong tabular performance with controlled complexity. Tune depth, learning rate, and number of trees together. Don't confuse the classical first-order derivation with XGBoost's second-order formulation.

DATA → PREPROCESS (if needed) → TRAIN / FIT → VALIDATE → TUNE → TEST → DEPLOY / MONITOR

03 · Hyperparameters & effect

• n_estimators: ↑ more stages; can reduce bias but overfit if uncontrolled.
• learning_rate: ↓ makes each tree weaker; usually pair with more trees.
• max_depth / max_leaf_nodes: ↑ tree complexity → bias ↓, variance ↑.
• subsample: <1 introduces stochasticity, often reduces variance.
• min_samples_leaf, regularization/pruning: control tree complexity.

04 · Bias ↔ Variance

Boosting primarily reduces bias by sequential correction, but too many/deep trees can increase variance. Learning rate ↓ + more trees often gives a smoother fit.

05 · When to consider

• Excellent for nonlinear tabular data and interactions.
• Strong when accuracy matters and data is structured/tabular.
Not ideal: very high-dimensional sparse data where linear models may be simpler; or when training simplicity/parallelism is paramount.
Watch: sequential training is harder to parallelize than RF.

06 · When NOT to reach for it

  • Don't choose by algorithm popularity; match the data geometry, scale, latency, interpretability and error cost.
  • Always compare against a simple baseline with the metric that reflects the real objective.

07 · Outliers / data issues

• Input outliers: trees are less distance-sensitive, but extreme feature values can affect split locations.
• Target outliers: loss-dependent; squared-error boosting is sensitive to extreme residuals. Robust losses can help.
• Label noise can be repeatedly chased by boosting → overfitting risk.
• Scaling generally unnecessary.

08 · Classification / multiclass

• Binary classification commonly uses a differentiable classification loss and additive tree scores converted to probabilities.
• Multiclass uses a multiclass loss with class-specific scores/updates; implementation details vary.

09 · Interview decision cue

Think GBDT when you want strong tabular performance with controlled complexity. Tune depth, learning rate, and number of trees together. Don't confuse the classical first-order derivation with XGBoost's second-order formulation.

07 / 09

XGBoost

A highly regularized, optimized gradient-boosted tree system using first- and second-order loss information.

01 · Computation — remember this

At each boosting round: compute gradient gᵢ and Hessian hᵢ of the loss → evaluate candidate splits using aggregated G/H statistics → choose splits with positive gain → compute leaf weight using regularized objective, conceptually w* = −G/(H+λ) → add tree with learning rate.
Second-order: Taylor expansion uses both gradient and curvature (Hessian).
Regularization: explicit L1/L2-style controls + tree complexity penalty help prevent overfitting.

02 · Algorithm in one flow

Consider when tabular predictive performance is a priority and you can tune carefully. Avoid unnecessary complexity when logistic/linear/tree baseline already meets requirements.

DATA → PREPROCESS (if needed) → TRAIN / FIT → VALIDATE → TUNE → TEST → DEPLOY / MONITOR

03 · Hyperparameters & effect

• learning_rate, n_estimators: slower learning + more trees often smoother.
• max_depth: ↑ → more complex, bias ↓/variance ↑.
• min_child_weight: ↑ → harder to create leaves, regularizes.
• subsample, colsample_bytree: stochasticity → often variance ↓.
• reg_lambda / reg_alpha: stronger regularization.
• gamma: minimum split gain; ↑ → fewer splits.

04 · Bias ↔ Variance

Boosting reduces bias through sequential corrections; depth/trees too high can raise variance. Subsampling/column sampling/regularization counter variance.

05 · When to consider

• Strong default for challenging tabular problems.
• Excellent when nonlinearities/interactions and performance matter.
• Rich regularization and practical controls.
Not ideal: if a simple linear model is sufficient, or if interpretability/latency constraints favor simpler models.
Use: when you want a highly tunable boosted-tree system.

06 · When NOT to reach for it

  • Don't choose by algorithm popularity; match the data geometry, scale, latency, interpretability and error cost.
  • Always compare against a simple baseline with the metric that reflects the real objective.

07 · Outliers / data issues

• Input outliers: usually less sensitive than KNN/linear models because trees split by thresholds; extreme values can still affect split candidates.
• Target outliers: loss-dependent; squared-error objective can chase extreme residuals. Robust/custom objectives may help.
• Scaling generally unnecessary.
• Missing values can be handled natively depending on configuration/version.

08 · Classification / multiclass

Supports multiclass objectives directly; internally learns class-related score updates rather than requiring manual OvR.

09 · Interview decision cue

Consider when tabular predictive performance is a priority and you can tune carefully. Avoid unnecessary complexity when logistic/linear/tree baseline already meets requirements.

LightGBM

A fast gradient-boosted tree framework optimized for large tabular datasets using histogram-based learning and leaf-wise growth.

01 · Computation — remember this

Histogram: continuous feature values are bucketed into bins → split search operates on bin statistics instead of every unique value.
Leaf-wise growth: among candidate leaves, split the leaf with the largest loss reduction rather than growing all leaves level-by-level.
Gradient boosting: sequentially adds trees/leaf expansions to reduce loss.
Large-data optimizations: histogram methods + techniques such as GOSS/EFB can improve speed/memory in suitable settings.

02 · Algorithm in one flow

Think LightGBM for large tabular data, speed, many features, and strong nonlinear performance. Be cautious on small/noisy data and aggressively regularize leaf-wise models.

DATA → PREPROCESS (if needed) → TRAIN / FIT → VALIDATE → TUNE → TEST → DEPLOY / MONITOR

03 · Hyperparameters & effect

• num_leaves: key complexity knob; ↑ → lower bias, higher variance.
• max_depth: cap tree depth.
• learning_rate, n_estimators: trade speed/fit.
• min_child_samples: ↑ regularization.
• feature_fraction, bagging_fraction: sampling/regularization.
• lambda_l1/l2: regularization.
• max_bin: histogram resolution vs memory/speed.

04 · Bias ↔ Variance

Leaf-wise growth can reduce bias faster than level-wise growth but can overfit more easily. Regularize leaf count, minimum data per leaf, depth, sampling, and L1/L2.

05 · When to consider

• Excellent for large/complex tabular datasets and fast training.
• Often very strong with many rows/features.
Not ideal: tiny datasets where simpler models are enough, or when leaf-wise growth is left uncontrolled and overfits.
Critical: tune num_leaves with min_child_samples/max_depth.

06 · When NOT to reach for it

  • Don't choose by algorithm popularity; match the data geometry, scale, latency, interpretability and error cost.
  • Always compare against a simple baseline with the metric that reflects the real objective.

07 · Outliers / data issues

• Input outliers: tree-based thresholding makes it relatively robust; extreme values can still affect binning/splits depending on distribution.
• Target outliers: objective-dependent; squared-error can chase extreme y/residuals.
• Scaling generally unnecessary.
• Histogram binning is a major computational optimization.

08 · Classification / multiclass

Direct multiclass objectives are supported; model learns class-specific outputs under the chosen multiclass loss.

09 · Interview decision cue

Think LightGBM for large tabular data, speed, many features, and strong nonlinear performance. Be cautious on small/noisy data and aggressively regularize leaf-wise models.

Naive Bayes

A probabilistic classifier that combines Bayes' rule with a conditional-independence assumption.

01 · Computation — remember this

Bayes: P(y|x) ∝ P(y)·P(x|y).
Naive assumption: P(x₁,…,xₚ|y)=∏ⱼP(xⱼ|y).
Training: estimate class priors and feature likelihood parameters from training data.
Prediction: calculate posterior score for each class → choose highest posterior.
Common variants: Gaussian NB (continuous), Multinomial NB (counts), Bernoulli NB (binary features).

02 · Algorithm in one flow

Consider for text/count/binary features, fast baselines, small datasets, and situations where the independence assumption is tolerable. Avoid if feature dependencies are central to the problem.

DATA → PREPROCESS (if needed) → TRAIN / FIT → VALIDATE → TUNE → TEST → DEPLOY / MONITOR

03 · Hyperparameters & effect

• Variant choice is often more important than a numeric hyperparameter.
• var_smoothing in GaussianNB: stabilizes tiny variances; ↑ adds more smoothing.
• alpha in Multinomial/Bernoulli variants: additive smoothing; ↑ more smoothing, less sensitivity to rare counts.
• priors/class_prior can encode prior probabilities.

04 · Bias ↔ Variance

Usually high bias because of the strong independence assumption, but low variance and low data requirements. Smoothing can reduce variance from rare features at the cost of bias.

05 · When to consider

• Very fast; excellent baseline for text/count features and small datasets.
• Works surprisingly well despite the independence assumption when ranking classes matters more than perfectly modeling dependence.
Not ideal: strongly dependent features where probability calibration/structure matters heavily.
Consider: when speed and high-dimensional sparse features dominate.

06 · When NOT to reach for it

  • Don't choose by algorithm popularity; match the data geometry, scale, latency, interpretability and error cost.
  • Always compare against a simple baseline with the metric that reflects the real objective.

07 · Outliers / data issues

• Input outliers: effect depends heavily on variant. GaussianNB can be affected by extreme continuous values because mean/variance estimates shift.
• Target outliers: classification labels that are wrong can distort priors/likelihood estimates.
• Scaling is generally not required for the probability model itself, but feature preprocessing still matters for the chosen variant.

08 · Classification / multiclass

Naturally multiclass: estimate priors/likelihoods for each class and select the largest posterior.

09 · Interview decision cue

Consider for text/count/binary features, fast baselines, small datasets, and situations where the independence assumption is tolerable. Avoid if feature dependencies are central to the problem.

Model Selection — What should I think first?

Choose based on data + objective, not because one algorithm is universally “best”.

Fast decision tree

Need regression? → Linear baseline → Tree ensemble if nonlinear/interactions → Boosting if performance priority
Need classification? → Logistic baseline → Tree ensemble if nonlinear/interactions → Boosting if performance priority
Huge sparse/count text? → Logistic / Naive Bayes are strong first checks
Small data + meaningful local similarity? → KNN can work
Need very little preprocessing / mixed scales? → Trees / RF / boosting
Need interpretability? → Linear/logistic or constrained tree
Need fast training + easy parallelism? → RF often easier than sequential boosting
Large tabular + speed? → LightGBM is a strong candidate

Linear / Logistic

  • Relationship/boundary roughly linear
  • Interpretability and stable baseline matter
  • High-dimensional sparse features
  • Regularization controls variance

KNN

  • Neighborhood similarity is meaningful
  • Small/medium dataset
  • Scaling + distance are trustworthy
  • Avoid high dimensionality / huge inference load

Tree / RF

  • Nonlinearity + interactions
  • Minimal scaling/preprocessing
  • RF = robust variance reduction
  • Good tabular baseline

GBDT / XGBoost / LightGBM

  • Tabular performance is priority
  • Nonlinearities + interactions
  • Tune complexity + learning rate + number of trees
  • Boosting can chase noise if overpowered

Evaluation Metrics — Classification

Metric follows the error you actually care about.

Confusion matrix → the foundation

Pred +Pred −
Actual +TPFN
Actual −FPTN
Precision = TP/(TP+FP) → among predicted positives, how many are correct.
Recall / TPR = TP/(TP+FN) → among actual positives, how many found.
Specificity / TNR = TN/(TN+FP) → among actual negatives, how many correctly rejected.
FPR = FP/(FP+TN), FNR = FN/(FN+TP).

Accuracy

Correct / all. Good when classes are reasonably balanced and FP/FN costs are similar. Danger: misleading under severe imbalance.

F1

2PR/(P+R). Good when precision and recall both matter. Fβ weights recall more when β>1 and precision more when β<1.

ROC-AUC

Ranks positives above negatives across thresholds using TPR vs FPR. Useful broad discrimination metric; can look overly optimistic under extreme imbalance.

PR-AUC

Precision–recall tradeoff. Particularly informative when the positive class is rare and finding positives is the focus.

Macro vs Weighted vs Micro

  • Macro: average metric per class → each class equal weight.
  • Weighted: weighted by class support → majority classes dominate more.
  • Micro: aggregate TP/FP/FN globally → frequent classes dominate.

What should I report?

ScenarioThink first
Balanced + equal costsAccuracy + confusion matrix; add F1 if useful.
Rare fraud / positive detectionPR-AUC + precision/recall at an operating threshold; confusion matrix.
Missing a positive is costlyRecall/TPR; choose threshold accordingly; report precision too.
False alarms are costlyPrecision / specificity; tune threshold.
Multiclass with minority classes importantMacro F1 + per-class metrics + confusion matrix.
Need threshold-independent rankingROC-AUC or PR-AUC depending on prevalence/problem.

Evaluation Metrics — Regression + Validation

Choose the metric that matches the business meaning of error.

MAE

mean |y−ŷ|. Same units as target. Robust-ish to outliers compared with RMSE. Easy to explain: “average absolute error”.

RMSE

√mean((y−ŷ)²). Same units as target. Penalizes large errors more strongly. Good when big misses are especially costly.

R²

1 − SSE/SST. Relative variance-explanation measure. Useful alongside MAE/RMSE, but not a direct business error unit. Can be negative on poor test predictions.

Metric choice

If you care about…Prefer / emphasize
Typical absolute errorMAE
Large mistakes disproportionately costlyRMSE
Relative fit / variance explainedR² + an error metric
Outlier-resistant summaryMAE (but investigate why outliers exist)

Validation workflow — don't contaminate the answer

Split data correctly → TRAIN only preprocessing/model fitting → CV on training data → tune hyperparameters → lock final pipeline → evaluate once on untouched TEST → report uncertainty / subgroup performance where appropriate.
  • Fit scaler/encoder/imputer/SMOTE inside the training fold, not before CV.
  • Use Pipeline + ColumnTransformer to keep preprocessing attached to the model.
  • For time-dependent data, use a time-aware split rather than random CV when random splitting leaks future information.
  • Choose the metric before tuning so the search objective matches the real goal.

Overfitting signal

Train score excellent + validation/test much worse → variance/overfit. Try simpler model, stronger regularization, more data, less depth, fewer leaves, fewer trees, or better validation.

Underfitting signal

Train and validation both poor → bias/underfit. Increase useful complexity, improve features, reduce excessive regularization, or use a more expressive model.

Class Imbalance + Final Interview Recall

The fastest mental checklist before you train or discuss a classifier.

Class imbalance — what changes?

  • Accuracy can become meaningless: predicting the majority class can look excellent.
  • Inspect confusion matrix, per-class precision/recall, macro F1, and PR-AUC where positive rarity matters.
  • Training: class weights, appropriate resampling, or specialized objectives can change the learning emphasis.
  • SMOTE: create synthetic minority samples only within training folds; never oversample before the train/validation split.
  • Threshold: model probability ≠ final business decision. Select threshold using validation data and FP/FN costs.

Outlier mental model

  • Linear / logistic: potentially influential.
  • KNN: distance-sensitive; very sensitive to feature extremes.
  • Trees: generally less sensitive in X-space; target outliers still matter for squared-error regression.
  • Boosting: can chase noisy/extreme residuals.
  • NB: variant-dependent; Gaussian estimates can shift.

Scaling mental model

  • Usually needed: KNN, logistic/linear with regularization/optimization, many distance/gradient-based methods.
  • Usually unnecessary: DT, RF, GBDT, XGBoost, LightGBM, Naive Bayes probability model.
  • Always fit transforms on training data only.
