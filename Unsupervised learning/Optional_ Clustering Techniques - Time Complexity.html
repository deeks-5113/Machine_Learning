Clustering Algorithms — Time Complexity, Deep Dive

A step-by-step, intuition-first walkthrough of why K-Means, K-Means++, Hierarchical Clustering, GMM, and DBSCAN cost what they cost — plus how to decide which one to actually reach for, and how teams do this in production.

01The Only Framework You Need

Read this before anything else

Don't memorize Big-O formulas. For any algorithm — clustering or otherwise — ask four questions in order:

1
What operation does it repeat? (a distance check, a probability calculation, a merge…)
2
How many times does it repeat that operation? (once per point? once per pair? once per point per centroid?)
3
How expensive is one operation? (a quick lookup, a scan across d features, or a matrix inversion?)
4
Does it repeat over multiple iterations? If yes, multiply everything by t.

Every formula in this note is just the answer to these four questions, multiplied together.

Notation used throughout

SymbolMeaning
nNumber of data points
kNumber of clusters (or Gaussian components)
dNumber of features / dimensions
tNumber of iterations until convergence
εNeighborhood radius used by DBSCAN
Nuance worth remembering When you see O(n²), the number of features d is usually being treated as a fixed constant and hidden. Written out fully, one distance calculation across d features costs O(d) — so a "quadratic" algorithm is often really O(n²d).

02K-Means

K-Means repeats two steps until the centroids stop moving:

1
Assignment: every point finds its nearest centroid.
2
Update: every centroid moves to the mean of its assigned points.
Every point (dot) compares itself against every centroid (✕). Line color shows which comparison "wins" — that's n × k comparisons, each costing O(d) to look across features.

Deriving the cost

With n points and k centroids, every point must be compared to every centroid — that's n × k comparisons. Each comparison looks across d features, so one comparison costs O(d).

$O(n \times k \times d) = O(nkd)$Assignment step, one iteration

The update step touches each point once to recompute means — O(nd) — which is smaller than the assignment step, so it doesn't change the dominant term.

$O(nkd)$Total cost, one full iteration

K-Means repeats assignment + update until centroids stabilize (or a max-iteration cap is hit), so multiply by t:

$O(nkdt)$Overall K-Means
In one line Every iteration, every point checks every centroid — that's n × k comparisons. Each comparison looks across d features, giving O(nkd) per iteration. Repeat for t iterations: O(nkdt).

03K-Means++

K-Means++ changes only how centroids are initialized — the assignment/update loop afterward is identical to plain K-Means.

Top row: plain K-Means (cheap random start, can get unlucky). Bottom row: K-Means++ spends a little extra work up front picking well-spread starting centroids, using each point's squared distance to the nearest already-chosen centroid as a selection probability.

Picking each new centroid requires computing distances from every point to the already-chosen centroids — an extra O(nkd)-scale cost, paid once, before the main loop starts.

Takeaway K-Means++ total cost = (one-time smarter initialization) + (normal K-Means iterations). It doesn't change the complexity order of growth — it changes how many iterations you typically need to converge, and how good the final clusters are.

04Hierarchical Agglomerative Clustering

Forget the word "hierarchical" for a second. The algorithm is really answering one question, over and over: "which two clusters are closest right now, so I can merge them?"

Each horizontal bar is a merge. n − 1 merges happen in total. The height of a merge shows how far apart the two clusters were — cut the tree at any height to get a flat clustering.

Step 1 — pairwise distances

With n points, every point needs a distance to every other point. The number of pairs grows as:

$O(n^2)$pairwise distances (and the memory to store them)
The distance matrix grows as n². Going from 4 points to 8 points (2×) turns 16 cells into 64 cells (4×) — this is what "quadratic" looks like in memory.

Why a naive implementation can hit O(n³)

After each merge, the algorithm must find the next closest pair. A naive implementation re-scans a large part of the structure to find that minimum, and this happens roughly n times (one merge per step):

$O(n^3)$naive: n merges × O(n²) search per merge
Common misconception "Hierarchical clustering is always O(n³)." That's only true for one specific (naive) way of writing it — not for the algorithm itself.

Why you'll see three different numbers for the same algorithm

O(n²), O(n² log n), and O(n³) are not competing answers — they're the same algorithm implemented three different ways. The question that changes the cost each time is: "once I've merged two clusters, how do I find the next closest pair?"

ImplementationTimeWhy
Naive O(n³) ~n merges happen. After each one, it re-scans the whole O(n²) distance structure from scratch to find the next closest pair.
Generic, using a heap (priority queue) O(n² log n) ~n merges happen. A heap finds the current closest pair in O(log n) instead of rescanning everything — but ~n heap entries still need updating after every merge.
Specialized ("nearest-neighbor chain") O(n²) Follows chains of "who's your nearest neighbor" and merges the moment it finds two clusters that pick each other — explained step by step below.

What is "nearest-neighbor chain", in plain terms?

This is the part that trips most people up, so slow down here. The naive and heap versions both do the same kind of work at every merge: ask the whole dataset "who is closest to whom, right now?" That global question is what's expensive to keep re-asking. The nearest-neighbor chain trick avoids ever asking it.

1
Start at any cluster. Call it your current chain.
2
Ask only that one cluster: "who is your single nearest neighbor?" Hop to it.
3
Ask the new cluster the same question, and hop again. Keep hopping, building a chain.
4
Eventually you'll hop to a cluster whose nearest neighbor is the cluster you just came from. That's a mutual pair — two clusters that each independently picked each other as their closest match.
5
A mutual pair is always safe to merge immediately (for single/complete/average/Ward linkage) — no global check needed. Merge them, step back one link in the chain, and keep hopping from there.
start → hop 1 → hop 2 lands on a cluster whose own nearest neighbor is the one you just came from — hop 3 points back. That reciprocal pair merges immediately, no global search needed.
Why this ends up at O(n²) overall Every hop only asks one cluster a "who's nearest to just you" question — cheap, local work. A cluster can only join and leave chains a limited number of times across the entire run (not once per merge, globally). Add up all that local hopping across the whole algorithm and it totals O(n²) — instead of O(n³) (rescanning everything) or O(n² log n) (maintaining one giant heap for everyone at once).
O(n²)memory — this floor applies to every implementation above, no exceptions
The one thing to remember Whichever implementation you use, you cannot escape storing ~n² distances in memory. Time can range from O(n²) (best, specialized) to O(n³) (worst, naive) — and when someone just says "hierarchical clustering is O(n²)" or "O(n³)", ask which implementation they mean.
The practical bottleneck Long before CPU time becomes the problem, memory does. At n = 100,000 points, a full distance matrix needs ~10 billion entries — this is usually what kills hierarchical clustering on large datasets, not the compute.

05Gaussian Mixture Models (GMM)

K-Means asks "which centroid is closest?" GMM asks a richer question: "what's the probability this point belongs to each Gaussian component?" That extra richness is exactly what makes it more expensive.

Every point belongs 100% to exactly one region.
A point in an overlap (white dot) gets a probability for each component.

Expectation–Maximization

1
E-step: for every point, compute its responsibility under every Gaussian component.
2
M-step: re-estimate each Gaussian's mean and covariance matrix.

Why the covariance matrix changes everything

With d features, each component's covariance matrix is d × d.

Every cell filled — models relationships between all feature pairs. Inversion/determinant ≈ O(d³).
Only the diagonal filled — assumes features are independent. Much cheaper, roughly O(d).

Cost of the E-step

Every point is evaluated under every Gaussian (n × k), and each evaluation involves d-dimensional matrix/vector operations:

$O(nkd^2)$

Cost of covariance operations

Inverting / taking the determinant of a d × d matrix is roughly cubic in d, across k components:

$O(kd^3)$
$O(nkd^2 + kd^3)$full-covariance GMM, one EM iteration
$O\big(t(nkd^2 + kd^3)\big)$overall, t EM iterations
The key intuition In GMM, the feature count d is dangerous in a way it isn't for K-Means — it appears cubed. Double your features and covariance operations get roughly 8× more expensive. This is why GMM struggles in high dimensions unless you constrain the covariance structure or reduce dimensionality first.

06DBSCAN

DBSCAN's core operation is a single repeated question: "which points are within ε of this point?" — a neighborhood query.

Core points have ≥ MinPts neighbors within ε. Border points sit on the edge of a core point's neighborhood. Noise points belong to no cluster.

Naive search

Checking one point X against every other point costs O(n). Doing this for every point:

$O(n^2)$naive, all points (O(n²d) if you count the d-feature cost per distance)

Making it faster with spatial indexing

Instead of comparing against all n points, spatial trees narrow the search to a small region — often O(log n) per query in favorable, low-dimensional conditions.
$O(n \log n)$indexed DBSCAN — one query costs O(log n), for all n points

Why you'll see two different numbers for the same algorithm

O(n²) and O(n log n) are the two ends of one spectrum, not two different facts about DBSCAN. What moves you along that spectrum is a single question: "does the spatial index actually manage to skip most of the points, or not?"

SituationCost of one queryTotal (n points)Why
No index (brute force), or an index in high dimensions O(n) O(n²) Every query still has to look at every other point, because there's no reliable shortcut to skip the far-away ones.
Spatial index (KD-tree / Ball-tree), low dimensions O(log n) O(n log n) The tree quickly rules out entire regions of far-away points, so each query only touches a small nearby slice.
Curse of dimensionality Spatial indexes lose their advantage as d grows — in high dimensions, "nearby" stops being a meaningful shortcut, distances between points start looking similar to each other, and query cost drifts back from O(log n) toward O(n) per point — i.e. the whole algorithm drifts back toward O(n²). This is one of the clearest examples of the curse of dimensionality in action.
The one thing to remember DBSCAN is never "just O(n²)" or "just O(n log n)" — it's O(n²) at worst (no index, or high dimensions) and O(n log n) at best (a working spatial index in low dimensions). Where your data lands depends on dimensionality, not on the algorithm itself.

07Space Complexity — How Much Memory Does Each Algorithm Need?

Every formula so far has measured time — how many operations happen. There's a second, equally important question that's easy to forget: how much do you need to hold in memory at once? The two don't always move together — an algorithm can be fast but memory-hungry, or slow but memory-light. Hierarchical and DBSCAN, coming up below, are the clearest example of exactly that split.

Ask the same kind of question — for memory instead of time
1
What do you have to keep in memory at the same time? (raw points, a distance matrix, probabilities, a tree structure…)
2
How many of those things are there?
3
How big is each one?
4
Does it grow across iterations, or stay fixed? Unlike time, memory usually does not keep growing with more iterations — you overwrite last iteration's numbers instead of keeping every old copy around.

K-Means & K-Means++

You need the k centroids (O(kd)) and one cluster-label per point (O(n)). The dataset itself (O(nd)) has to be in memory too, but that's true no matter which algorithm you run — it's not a cost specific to K-Means.

O(kd + n)extra memory, beyond the dataset itself

K-Means++ needs one more small array, only during initialization: the distance from each point to the nearest centroid chosen so far (O(n)), freed once initialization finishes. It doesn't change the complexity class.

Hierarchical

You already met this one: a full pairwise distance matrix between all remaining clusters.

O(n²)memory — required by every implementation, naive or specialized

This is the one algorithm here where a faster time implementation buys you nothing in memory — the nearest-neighbor chain trick from the last section speeds up time only, not space.

GMM

Two things dominate: the responsibility of every point under every component (n × k numbers), and each component's covariance matrix (d × d, ×k components).

O(nk + kd²)full covariance

Switching to diagonal covariance (see Section 05) drops the second term to O(kd) — another reason it's the default choice once d gets large.

DBSCAN

This is the one that surprises people: DBSCAN does not need a full pairwise distance matrix. It only ever needs the neighborhood of one point at a time — computed, used, and thrown away before moving to the next point. What it keeps around is small: one visited/label flag per point, and — if you're using one — the spatial index itself.

O(n)typical — labels + index structure, not a distance matrix

The only way DBSCAN's memory approaches O(n²) is a pathological case — an ε so large that every point ends up in every other point's neighborhood at once. That's rare in practice, not the normal cost of running it.

09Which Algorithm Should You Actually Try?

There is no single "best" clustering algorithm — complexity is only one input. The honest answer is a small decision tree built around what your data and problem actually look like.

A practical decision tree — not a law of nature. Real projects often try two or three of these and compare with a validation metric (e.g. silhouette score) before committing.
Rules of thumb
  • Default first attempt: K-Means. It's the fastest to run, the easiest to explain to a non-technical stakeholder, and a good sanity check even if you end up using something else.
  • Clusters that aren't blobs (crescents, rings, geospatial "dense regions" separated by sparse ones) → K-Means will actively mislead you; use DBSCAN/HDBSCAN.
  • A point can genuinely belong to more than one group (e.g. a customer who shops like two segments at once) → GMM's soft assignments are the right shape of answer, not just a computational choice.
  • You want to show a business stakeholder "here's how granular we can get" → a dendrogram from hierarchical clustering is the only one of these that gives that for free, but only feasible while n is small.

10How Industry Actually Decides

In practice, complexity is rarely the first filter teams apply — it's the filter that decides which of the otherwise-reasonable options is affordable to run. The order usually looks like this:

1
What does the business need to know? Hard segments for a dashboard? Probabilities for a recommendation model? An anomaly flag? This picks the algorithm family before anyone thinks about n.
2
What shape do the clusters actually have? Teams usually eyeball a 2D projection (PCA/UMAP/t-SNE) first — this alone rules out K-Means for a lot of real-world data.
3
What's the data scale, and how often must it re-run? A one-time offline analysis on 50k rows tolerates O(n²). A pipeline re-clustering 20M events every hour does not.
4
Now apply complexity to see which of the shape-appropriate, business-appropriate options are actually feasible at that scale and refresh rate — and that's when engineering starts optimizing (indexing, sampling, dimensionality reduction, approximation).

Typical choice by dataset scale

Scale (n)What's typically usedWhy
Small — up to ~10k–50kHierarchical, GMM, or plain K-MeansO(n²) or O(n³) is affordable; dendrograms and soft assignments are cheap enough to be worth it.
Medium — ~50k–1MK-Means / K-Means++, DBSCAN with a spatial indexO(n²) methods start to hurt; indexed neighborhood search keeps DBSCAN usable.
Large — 1M+ / streamingMiniBatch K-Means, HDBSCAN on a sample, approximate nearest-neighbor search (FAISS, Annoy, HNSW)Exact O(n²) approaches are no longer feasible; teams trade a small amount of accuracy for speed.

Patterns that show up again and again

  • Reduce dimensions before clustering. Running PCA/UMAP down to a handful of dimensions before GMM or DBSCAN directly attacks the d term in O(kd³) or the curse-of-dimensionality problem in spatial indexing.
  • Sample, cluster, then assign the rest. Fit an expensive algorithm (e.g. hierarchical) on a representative sample, then assign the remaining points to the nearest resulting cluster — gets the interpretability without paying O(n²) on the full dataset.
  • Approximate nearest neighbors at scale. Libraries like FAISS/Annoy/HNSW turn an O(n) or O(n²) neighbor search into something close to O(log n) in practice, which is what makes DBSCAN-style approaches viable on large datasets.
  • MiniBatch variants for streaming/online settings. MiniBatch K-Means updates centroids on small random batches instead of the full dataset each iteration — trading a little quality for a large drop in per-iteration cost.
  • Validate before committing. Silhouette score, Davies–Bouldin index, or simply a business-metric backtest usually settles ties between two algorithms that are both computationally feasible — complexity narrows the shortlist, it doesn't pick the winner.
The one sentence version Industry doesn't ask "which algorithm has the best Big-O?" — it asks "given what I need to know, what my clusters look like, and how much data I have to process how often, which of the algorithms that fit my problem can I actually afford to run?"
