Evaluating a classifier — the problem statement

We now know how to build a classifier (logistic regression, and later KNN, Naive Bayes, trees). The remaining question: once it's built, how do we know if it's actually any good? Just like regression has R², RMSE, MAE — classification needs its own set of evaluation tools.

Accuracy — formula & example

Accuracy = (correct predictions) / (total predictions)

Example: a model checks 100 emails, correctly labels 90 of them (spam or not-spam).

Accuracy = 90/100 = 0.90 (90%)

Where accuracy goes wrong, and why

Accuracy silently assumes the classes are roughly balanced. The moment one class dominates, a model that does nothing useful can still score deceptively high.

scenarioa model that always predicts the majority classaccuracyactually useful?
1000 patients, 50 sick (5%)always predicts "healthy"95%0 sick patients caught
95% accuracy, and it never once did its job. This is exactly why we need a tool that looks inside the predictions, not just at the overall correct/incorrect count — the confusion matrix.
Looking inside the predictions

Imbalanced data & the confusion matrix

The confusion matrix is a simple 2×2 grid that splits every prediction into one of four buckets, comparing what the model predicted against what actually happened.

How to plot it

1 One axis = actual truth (Positive / Negative). The other axis = model's prediction (Positive / Negative).
2 Each cell counts how many rows fall into that combination.
3 The diagonal = correct. The off-diagonal = the two different ways to be wrong.
Actual: PositiveActual: Negative
Pred:PositiveTPFP
NegativeFNTN

Accuracy, rewritten from the confusion matrix

Accuracy = (TP + TN) / (TP + TN + FP + FN)

Same formula as before — just now expressed in terms of the four buckets, which is what lets us build every other metric from here on.

Every term, in plain English

termformulaplain English
True Positive (TP)—Model said positive, actually positive — correct catch
True Negative (TN)—Model said negative, actually negative — correct clear
False Positive (FP)—Model said positive, actually negative — false alarm
False Negative (FN)—Model said negative, actually positive — missed case
metricformulaplain English — "out of..."
PrecisionTP/(TP+FP)Out of everything I predicted positive, how many actually were?
Recall / TPRTP/(TP+FN)Out of all actual positives, how many did I correctly find?
TNR (Specificity)TN/(TN+FP)Out of all actual negatives, how many did I correctly reject?
FPRFP/(FP+TN)Out of all actual negatives, how many did I falsely flag as positive?
FNRFN/(FN+TP)Out of all actual positives, how many did I miss?
Notice the pattern linking them: Recall and FNR both look at actual positives (they add to 1). TNR and FPR both look at actual negatives (they add to 1). Precision is the odd one out — it looks at predicted positives, not actual ones.
Two edge cases worth knowing: if TP=0, Precision's denominator can be 0 (undefined) unless FP is also 0; and Recall=TP/(TP+FN)=1 only when FN=0 — i.e. every actual positive was caught, with zero missed.
The knob that controls everything

How threshold moves precision & recall

Recall the model outputs a probability, and we apply a threshold to get a 0/1 label. Move that threshold, and every rate above shifts with it.

Decrease the threshold

More rows get labeled "positive." You catch more real positives (recall ↑) — but you also wave through more false alarms (FP ↑, precision ↓).

Increase the threshold

Fewer rows get labeled "positive," only the most confident ones. Precision ↑ — but you now miss more borderline real positives (FN ↑, recall ↓).

When both matter — F1 score

examplewhy both false positives AND false negatives hurt
Fake news vs. not-fake-news detectionMissing real fake news lets misinformation spread (recall); wrongly labeling real news as fake damages trust and free speech (precision)
Good vs. bad candidate — HR screeningMissing a great candidate loses talent (recall); wrongly advancing a bad candidate wastes interview time and hiring budget (precision)

Why not just average precision and recall?

Take Precision=1.0, Recall=0.01 — a model that's right every time it dares to guess "positive," but only guesses once:

Arithmetic mean = (1.0+0.01)/2 = 0.505  — looks "medium," but the model catches almost nothing

The fix — harmonic mean

F1 = 2 · (Precision · Recall) / (Precision + Recall)
F1 = 2×(1.0×0.01)/(1.0+0.01) = 0.0198
The harmonic mean collapses toward whichever number is smaller — it can't be fooled by one great score hiding one terrible one. That's precisely why F1, not a plain average, is the standard when both precision and recall matter.
A threshold-free view

ROC-AUC — the name, and its history

ROC = Receiver Operating Characteristic   |   AUC = Area Under the Curve
The name has nothing to do with machine learning originally — it comes from radar signal detection during World War II. Imagine an army with a radar. The radar continuously receives signals, and its job is to decide: incoming signal — enemy aircraft, yes or no? The radar receiver could be tuned more sensitive (catch more real aircraft, but more false alarms too) or less sensitive (fewer false alarms, but risk missing a real threat). The curve describing that receiver's trade-off as its sensitivity dial was adjusted was called its "operating characteristic." Hence: Receiver Operating Characteristic.
Today's "sensitivity dial" is just the probability threshold. Same trade-off, seventy-plus years later.

Graphical representation

Plot TPR (Recall) on the y-axis against FPR on the x-axis. Every point on the curve corresponds to one threshold. Sweep the threshold from strictest to most lenient, and trace the path.

Top-left corner = ideal (high TPR, low FPR). Diagonal = pure chance.

The probability interpretation

AUC = P( a randomly picked positive scores higher than a randomly picked negative )

This is the single most useful sentence to remember about AUC. AUC=1.0 → every positive outranks every negative, perfect separation. AUC=0.5 → a random negative is just as likely to outscore a random positive as not — no better than a coin flip. AUC=0.0 → the model is perfectly backwards; flip its predictions and you'd get a perfect model.

Why ROC-AUC is required

Accuracy, precision, recall, F1 — all depend on one specific threshold. ROC-AUC summarizes performance across every possible threshold at once, letting you judge a model's raw separating power before ever committing to an operating point. This is essential when comparing two candidate models, or when the eventual threshold hasn't been decided yet.

Where ROC-AUC can go wrong

On heavily imbalanced data, FPR's denominator (FP+TN) is dominated by a huge negative class — so even a large number of false positives barely moves FPR, making the curve look better than it deserves.

count
Total positives1,000
Total negatives9,000
TP (caught)980 → Recall = 0.98
FP (false alarms)900 → FPR = only 0.10
Precision980/(980+900) = 0.521
FPR=0.10 looks great on a ROC curve — but that "small rate" is hiding 900 real false alarms. Precision tells the honest story: only 52% of everything flagged "positive" is actually correct. This is exactly the gap PR-AUC is built to close.
The imbalanced-data fix

The PR-AUC curve

Same sweep-the-threshold idea as ROC — but plot Precision (y-axis) against Recall (x-axis) instead of TPR vs FPR.

Precision typically falls as recall is pushed toward 1.0 — the trade-off, made visible
Why this helps on imbalanced data: Precision is built only from TP and FP — the huge negative class (TN) never dilutes it the way it dilutes FPR. PR-AUC stays honest exactly where ROC-AUC can be misleading.
