01 · the bridge

One raw score becomes K raw scores

In binary classification, every row got exactly one raw score \(F(x)\), squeezed through a sigmoid into one probability. With \(K=3\) classes — say A, B, C — that single number isn't enough to describe "how much do I believe this row is A, vs B, vs C." So the model keeps three separate raw scores per row:

Binary
x → one raw score → sigmoid → one probability
┌── F_A ├ x ──→ model ────├── F_B ├ └── F_C
This is the single biggest conceptual jump in this whole chapter. Everything else — gradients, Hessians, splits, leaf weights, learning rate — is machinery you already fully know. What's new is simply: there are now \(K\) of everything, one per class, and they interact through one new piece: softmax.
02 · the bridge

Softmax: turning K scores into K probabilities

Sigmoid took one raw score and squeezed it into \([0,1]\). Softmax takes all K raw scores together and turns them into a full probability distribution that sums to 1:

\[ p_{k}=\frac{e^{F_{k}}}{\displaystyle\sum_{j=1}^{K}e^{F_{j}}} \]

For 3 classes, spelled out completely:

\[ p_A=\frac{e^{F_A}}{e^{F_A}+e^{F_B}+e^{F_C}},\quad p_B=\frac{e^{F_B}}{e^{F_A}+e^{F_B}+e^{F_C}},\quad p_C=\frac{e^{F_C}}{e^{F_A}+e^{F_B}+e^{F_C}} \]
Notice every one of the three probabilities depends on all three raw scores, not just its own. That single fact is the root of an important subtlety we come back to in §20 — the three classes are never quite independent, because they all share the same denominator.
By construction, \(p_A+p_B+p_C=1\) always — softmax is exactly the multiclass generalisation of sigmoid, and reduces to it exactly when \(K=2\).
03 · the bridge

Before any tree exists: what should the model predict?

Ask yourself, properly: in the binary chapter, the initial prediction wasn't just assumed to be 0.5 — it was derived as \(p_0=\#\text{positive}/n\), the base rate. Shouldn't multiclass get the same treatment, \(n_k/n\) per class, instead of just declaring \(1/K\) for everyone?

Yes — and it's worth deriving properly here, because the "uniform 1/3" answer is secretly a special case, not a different rule.

Derive it the same way binary did: minimise the loss over a constant prediction

Exactly like the binary derivation, find the constant probability vector \(p=[p_A,p_B,p_C]\) (same for every row) that minimises total cross-entropy loss, subject to \(\sum_k p_k=1\):

\[ \min_{p}\ -\sum_k n_k\log p_k\quad\text{subject to}\quad\sum_k p_k=1 \]

where \(n_k\) is simply how many training rows actually belong to class \(k\).

Using a Lagrange multiplier \(\mu\) for the constraint, differentiate and set to zero:

\[ \frac{\partial}{\partial p_k}\left[-\sum_k n_k\log p_k+\mu\left(\sum_k p_k-1\right)\right]=-\frac{n_k}{p_k}+\mu=0\ \Rightarrow\ p_k=\frac{n_k}{\mu} \]

Substitute back into \(\sum_k p_k=1\) to solve for \(\mu\): \(\sum_k n_k/\mu=1\Rightarrow\mu=n\) (the total row count). Therefore:

\[ \boxed{p_k^{(0)}=\frac{n_k}{n}} \]
Exactly the same shape as binary's \(p_0=\#\text{positive}/n\) — just one base rate per class instead of one base rate for "positive." This is the general rule; \(1/K\) is not a separate assumption, it's what this formula gives you when every class happens to be equally represented.

Turning the base rate into a raw score

Binary needed \(F_0=\log(p_0/(1-p_0))\) because sigmoid needed inverting. Softmax inverts just as directly — if you want softmax to output exactly \(p_k\), simply set:

\[ F_k^{(0)}=\log(p_k^{(0)})=\log\!\left(\frac{n_k}{n}\right) \]

Check it: \(\text{softmax}(\log p)_k=\dfrac{e^{\log p_k}}{\sum_j e^{\log p_j}}=\dfrac{p_k}{\sum_j p_j}=\dfrac{p_k}{1}=p_k\) — recovers the base rate exactly, since probabilities already sum to 1.

So why did §3's original walkthrough just say "start at 0"?

Apply the formula to our actual dataset: 2 rows each of A, B, C, out of 6 total.

Classnkpk(0) = nk/nFk(0) = log(pk(0))
A22/6 = 0.333log(0.333) = −1.0986
B22/6 = 0.333log(0.333) = −1.0986
C22/6 = 0.333log(0.333) = −1.0986
Here's the key fact that resolves it: softmax is shift-invariant — adding the same constant to every class's raw score changes nothing:
\[ \text{softmax}(F+c)_k=\frac{e^{F_k+c}}{\sum_j e^{F_j+c}}=\frac{e^c\cdot e^{F_k}}{e^c\cdot\sum_j e^{F_j}}=\text{softmax}(F)_k \]

Our derived scores are \([-1.0986,-1.0986,-1.0986]\) — add \(c=+1.0986\) to every one (a valid shift, since it's the same amount added to all three) and you land exactly on \([0,0,0]\), with identical resulting probabilities. That's the entire resolution: "start at 0" is only ever correct when every class's base rate is equal — it happened to be true for our clean 2-2-2 dataset, so the simplified version and the properly-derived version are the same numbers in disguise.

This does not generalise to imbalanced data. Sigmoid, unlike softmax, is not shift-invariant — \(\sigma(F+c)\ne\sigma(F)\) in general — which is exactly why the binary chapter couldn't skip the \(\log(p_0/(1-p_0))\) derivation and just default to \(F=0\). For multiclass, if the class counts were, say, \(n_A=100,n_B=50,n_C=10\), starting every class at \(F=0\) would be genuinely wrong — it would silently assume a balanced dataset that doesn't exist. The correct, general initialisation — and what real implementations use — is \(\boxed{F_k^{(0)}=\log(n_k/n)}\), which only simplifies to a shared constant (equivalent to 0 after shifting) when the classes are balanced.
04 · the core jump

The key idea: one boosting iteration = K trees

In binary boosting, one iteration built one tree. With \(K=3\) classes, one iteration builds three — one dedicated tree per class, every single round:

Iteration 1 Current model │ ┌───────│───────└ ↓ ↓ ↓ Tree A Tree B Tree C │ │ │ ↓ ↓ ↓ correction correction correction for A for B for C
\[ \boxed{K=3\ \Rightarrow\ 3\text{ trees per boosting iteration}} \]
Do 3 boosting iterations with 3 classes and you've trained \(3\times3=\boxed{9}\) trees total — not 3. This single fact changes training cost, model size, and inference cost roughly \(K\)-fold versus binary classification, and it's worth internalising before any of the maths below.
05 · the core jump

The target, one-hot

A single label like "class A" needs to become something with the same shape as the model's output — 3 numbers, one per class:

True class\(y_A\)\(y_B\)\(y_C\)
A100
B010
C001
Exactly one entry is 1 (the true class), the rest are 0 — this is one-hot encoding, and it's what makes the loss and gradient formulas below work cleanly: comparing a full probability vector \([p_A,p_B,p_C]\) against a full target vector \([y_A,y_B,y_C]\), entry by entry.
06 · the core jump

Multiclass cross-entropy

Binary log loss generalises directly — sum the same "\(-y\log p\)" penalty across all K classes:

\[ \boxed{L_i=-\sum_{k=1}^{K}y_{ik}\log p_{ik}} \]

For 3 classes, spelled out:

\[ L_i=-y_{i,A}\log p_{i,A}-y_{i,B}\log p_{i,B}-y_{i,C}\log p_{i,C} \]
Because \(y\) is one-hot, only one term survives per row. If the true class is A (\(y_A{=}1,y_B{=}0,y_C{=}0\)):
\[ L_i=-\log p_{i,A} \]
Exactly the same shape as binary log loss — "penalise the log-probability the model assigned to the class that was actually true" — just now that probability comes from softmax over 3 scores instead of sigmoid over 1.
07 · the core jump

Deriving the gradient, in full — not just stating it

Substitute softmax into the loss

Start from \(L=-\sum_k y_k\log p_k\) with \(p_k=\dfrac{e^{F_k}}{\sum_j e^{F_j}}\):

\[ L=-\sum_k y_k\log\left(\frac{e^{F_k}}{\sum_j e^{F_j}}\right) \]

Use \(\log(a/b)=\log a-\log b\):

\[ L=-\sum_k y_k\left(F_k-\log\sum_j e^{F_j}\right)=-\sum_k y_kF_k+\left(\sum_k y_k\right)\log\sum_j e^{F_j} \]

Because \(y\) is one-hot, \(\sum_k y_k=1\) always — that whole factor simply disappears:

\[ L=-\sum_k y_kF_k+\log\sum_j e^{F_j} \]
Differentiate with respect to one class's raw score, \(F_k\)

The first term is linear in \(F_k\): \(\dfrac{\partial}{\partial F_k}\left(-\sum_j y_jF_j\right)=-y_k\). The second term needs the chain rule:

\[ \frac{\partial}{\partial F_k}\log\sum_j e^{F_j}=\frac{e^{F_k}}{\sum_j e^{F_j}}=p_k \]

Add both pieces together:

\[ g_k=\frac{\partial L}{\partial F_k}=-y_k+p_k \]
\[ \boxed{g_{ik}=p_{ik}-y_{ik}} \]
The exact same shape as binary classification's \(g=p-y\) — the only difference is there are now \(K\) of these, one per class, and \(p_k\) comes from softmax (which depends on all \(K\) scores) rather than sigmoid.

09 · the core jump

The Hessian — every calculation shown, plus an honest nuance

The diagonal second derivative, used by every implementation covered in this chapter:

\[ \boxed{h_k=p_k(1-p_k)} \]
Ask yourself: where does this actually come from, and how do you compute it for a real number?

Where it comes from: it's the second derivative of the loss with respect to \(F_k\) — literally, differentiate \(g_k=p_k-y_k\) once more with respect to \(F_k\). Since \(y_k\) is a fixed constant (the label doesn't move), only \(p_k\) contributes, and \(\dfrac{\partial p_k}{\partial F_k}=p_k(1-p_k)\) is a standard property of the softmax/sigmoid shape — the same derivative you already used in the binary chapter, just relabelled per class.

How to actually compute it, arithmetic spelled out: take whatever \(p_k\) is for that row and class, subtract it from 1, and multiply the two numbers together. That's it — no other inputs, no \(y\) involved at all.

Worked at initialisation, every class, full arithmetic

Every class starts at \(p_k=1/3\approx0.333\):

\[ h_A=p_A\times(1-p_A)=0.333\times(1-0.333)=0.333\times0.667=0.222 \]
\[ h_B=p_B\times(1-p_B)=0.333\times0.667=0.222,\qquad h_C=p_C\times(1-p_C)=0.333\times0.667=0.222 \]
All three come out identical here only because all three probabilities happen to be identical at initialisation. The moment the probabilities diverge (from round 2 onward), each class's \(h\) diverges too — shown next.
Classpyg=p−yh = p × (1−p)
A0.3331-0.6670.333 × 0.667 = 0.222
B0.33300.3330.333 × 0.667 = 0.222
C0.33300.3330.333 × 0.667 = 0.222
The honest nuance: the true multiclass Hessian is not just a single number per class — softmax couples every pair of classes, so the full second-derivative object is a \(K\times K\) matrix per row, with off-diagonal terms \(\partial^2L/\partial F_j\partial F_k=-p_jp_k\) for \(j\ne k\). Every implementation in this chapter uses the diagonal approximation \(h_k=p_k(1-p_k)\) — ignoring the cross-class curvature — because it lets each class's tree be built independently with the exact same \(G,H\)-based machinery you already know, at the cost of a slightly less precise second-order step. This is a deliberate, standard simplification, not an oversight.
10 · the core jump

How does a tree actually learn from these numbers?

Ask yourself: we now have three separate columns of \((g,h)\) per row — one per class. What do we do with them?

Treat each class's column as its own separate regression target, and build its own separate regression tree — exactly the same tree-building machinery from the GBDT/XGBoost/LightGBM chapters, just run three times:

Dataset │ ┌────────│────────└ ↓ ↓ ↓ Class A Class B Class C target column target column target column ↓ ↓ ↓ Tree A Tree B Tree C
Correction, important: "the same tree-building machinery" does not mean every implementation splits the same way internally. Classic GBDT never computes a Hessian \(h\) or a \(G,H\)-based Gain at all — it simply fits an ordinary CART regression tree (identical splitting rule to a plain DecisionTreeRegressor: minimise MSE / maximise variance reduction) to that class's pseudo-residual target. XGBoost and LightGBM are the ones that replace that plain MSE split with the \(G,H\)-weighted, regularised Gain formula. Full side-by-side, with the derivation of why they end up numerically related, is in §12.
What genuinely stays true for every implementation: this entire tree-building process happens three times, once per class, on that class's own target column, every single round — only the internal splitting rule differs.

12 · iteration 1, completely

Splitting: GBDT's plain MSE reduction vs XGBoost/LightGBM's G,H Gain

Multiclass doesn't force one specific tree-building method — it only forces "one tree per class." Which method that tree uses underneath is exactly the choice you already learned to make in the earlier chapters. Both versions below use the very same class-A/B/C residual/gradient columns from §11 — they just process them completely differently internally.

Classic GBDT

No gradient sums, no Hessian, no regularisation anywhere. An ordinary CART regression tree, splitting purely to minimise MSE / maximise variance reduction on the pseudo-residual target \(r\) — identical rule to a plain DecisionTreeRegressor:

\[ \Delta\text{MSE}=\text{SSE}_{\text{parent}}-\text{SSE}_{\text{left}}-\text{SSE}_{\text{right}} \]

XGBoost/LightGBM

Weight every row by its actual Hessian \(h_i=p_i(1-p_i)\), add L2 regularisation \(\lambda\):

\[ Gain_{\text{XGB}}=\frac12\left(\frac{G_L^2}{H_L+\lambda}+\frac{G_R^2}{H_R+\lambda}-\frac{G^2}{H+\lambda}\right)-\gamma \]

where \(H_L,H_R,H\) are true Hessian sums (§9), and \(\lambda=1,\gamma=0\) throughout this chapter.

To correct a common mix-up directly: GBDT does not internally compute anything called "\(G\)" or "\(H\)" or "Gain." It only ever computes MSE reduction, exactly as an ordinary regression tree would. The reason we can still write GBDT's splitting rule using \(G,H\)-shaped notation (below) is a mathematical coincidence worth deriving properly, not because GBDT is secretly doing a second-order calculation.
Why MSE reduction happens to look like the G,H formula, with H=row count

For a set of residuals with sum \(G\) and count \(n\), the sum of squared errors around the mean is:

\[ \text{SSE}=\sum_i r_i^2-\frac{G^2}{n} \]

Since \(\sum_i r_i^2\) splits additively across left and right rows (every row belongs to exactly one side), it cancels out of the reduction:

\[ \Delta\text{MSE}=\text{SSE}_{\text{parent}}-\text{SSE}_L-\text{SSE}_R=\frac{G_L^2}{n_L}+\frac{G_R^2}{n_R}-\frac{G^2}{n} \]
This is exactly the shape of the XGBoost Gain formula with \(H\to n\) (plain row count instead of a Hessian sum) and \(\lambda=\gamma=0\). That's the entire relationship: ordinary variance-reduction splitting can be written in \(G,H\)-shaped notation for easy comparison — it is not evidence that classic GBDT computes a Hessian. We use this notation purely so the two methods can sit side by side in the same table below.

On messier real data, the two methods can genuinely disagree on the winning split, precisely because XGBoost's version down-weights rows the model is already confident about (low \(h\)) and up-weights the ones it's still uncertain on (high \(h\), near \(p{=}0.5\)) — GBDT's plain MSE version has no such notion of "confidence," every row counts equally. One thing is true for both methods, though: each class's split search runs completely independently, on that class's own target column — the best split for Tree A has no obligation to match Tree B's or Tree C's.

Why the three trees can look completely different

Each tree is answering a genuinely different question:

TreeQuestion it's solving
Tree A"Where am I currently under-predicting class A?"

There is no requirement, anywhere in the math, that these three questions share an answer. In general, with more features and more complex data, the three trees can have completely different structures, use different features to split on, and reach different depths — they're independent regression trees that just happen to be trained in the same round, on the same rows, with different targets.

Leaf prediction, per class — both versions

GBDT leaf value

Just the plain mean of the pseudo-residuals \(r\) landing in that leaf — the same rule an ordinary regression tree uses at every leaf:

\[ w^*_{\text{GBDT}}=\text{mean}(r)=-\text{mean}(g)=-\frac{G}{n} \]

(\(G=\sum g\) here, in the gradient notation from §7–8; since \(r=-g\), the mean of the residuals is minus the mean of the gradients)

Hessian-weighted and regularised — the formula you already derived:

\[ w^*_{\text{XGB}}=-\frac{G}{H+\lambda} \]

19 · iterations 2 & 3

The complete algorithm

1
Initialise: \(F_{ik}^{(0)}=0\) for every row \(i\), every class \(k\) (or an implementation's chosen prior).
2
Softmax: \(p_{ik}=\dfrac{e^{F_{ik}}}{\sum_j e^{F_{ij}}}\).
3
Gradients & Hessians, per class: \(g_{ik}=p_{ik}-y_{ik}\), \(h_{ik}=p_{ik}(1-p_{ik})\) (diagonal approximation, §9).
4
For every class \(k\) separately: build a regression tree on that class's \((g,h)\) column — the exact histogram/leaf-wise/Gain machinery from earlier chapters, unmodified.
5
Leaf values: \(w_j^*=-G_j/(H_j+\lambda)\), per class, per leaf.
6
Update every class's raw score:
\[ F_{ik}^{(t)}=F_{ik}^{(t-1)}+\eta\, f_{k,t}(x_i),\qquad k\in\{A,B,C\} \]
7
Repeat from step 2, \(K\) trees at a time, until \(n\_estimators\) or early stopping.
20 · the subtlety

Are the K trees independent? No.

Ask yourself: Tree A, Tree B, and Tree C are trained separately, on separate gradient columns. Does that make them independent models?

No — they're coupled through the one thing they all share: softmax's denominator.

\[ p_A=\frac{e^{F_A}}{e^{F_A}+e^{F_B}+e^{F_C}} \]
Changing \(F_B\) alone changes \(p_A\) — even though nothing about class A's raw score moved. Every class's probability depends on every class's raw score, all at once.
Tree A changes F_A ↓ softmax ↓ ALL class probabilities change (A, B, AND C) ↓ gradients for ALL classes change, next round
This is why you cannot train the 3 trees in true isolation and expect the same result as joint boosting: Tree B's correction this round genuinely reshapes what Tree A's gradients will look like next round, purely through the shared softmax normalisation — even though Tree B never touches \(F_A\) directly.

24 · wrap-up

K trees, not one tree with K leaf values

A trap worth naming explicitly: it's tempting to imagine multiclass boosting as "one tree, whose every leaf just happens to store 3 numbers instead of 1." That's a valid abstract mathematical picture in some research formulations — but it is not the practical mechanism used by the GBDT/XGBoost/LightGBM implementations in this chapter.

The actual, practical picture, confirmed by every worked example above:

\[ \boxed{K\text{ separate class-specific trees, every single boosting round}} \]
Round 1 → Tree A + Tree B + Tree C Round 2 → Tree A + Tree B + Tree C Round 3 → Tree A + Tree B + Tree C
\[ \boxed{3\text{ rounds}\times3\text{ classes}=9\text{ trees total}} \]
Each of those 9 trees has its own splits, its own leaves, its own leaf values — entirely separate structures, coupled only through the shared softmax at prediction and gradient-computation time (§20). This directly explains why multiclass models are roughly \(K\) times larger and \(K\) times slower to train and to predict with, compared to an otherwise-identical binary model.
25 · wrap-up

Binary vs multiclass, side by side

Binary classification

one observation ↓ one raw score ↓ one probability ↓ one tree correction

Multiclass, K=3

one observation ↓ ┌─ F_A F_B F_C ─┐ ↓ Softmax ↓ ┌─ p_A p_B p_C ─┐ ↓ ┌─ g_A g_B g_C ─┐ ↓ ┌├─ Tree A ├─ Tree B ├─ Tree C ─┐ ↓ Update three raw scores ↓ Softmax again, repeat
In multiclass gradient boosting, the model maintains one raw score per class. At every boosting iteration, it builds one class-specific tree per class to correct those scores; softmax converts the updated scores into probabilities, and the class with the largest final probability is the prediction.
