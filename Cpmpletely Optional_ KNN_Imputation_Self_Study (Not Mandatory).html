The problem

Why Missing Data Needs a Real Strategy

Real datasets almost always have gaps — a customer skipped a form field, a sensor dropped a reading, a survey question went unanswered. Most ML models can't train on NaN directly. You have 3 broad choices:

ApproachWhat it doesDownside
Drop the rowDelete any row with a missing valueThrows away real, possibly valuable data
Mean/median/mode fillFill every gap with one global constantIgnores that different rows are genuinely different — one-size-fits-all guess
KNN ImputationFill the gap using similar ROWS' values for that featureMore compute, but a genuinely row-specific, informed guess
The core idea, in one line: "if you don't know a value, ask your most similar neighbors what theirs is." Exactly the same nearest-neighbor intuition as KNN classification/regression — just aimed at filling gaps instead of predicting a label.

Verified directly against sklearn's KNNImputer(n_neighbors=2): it returns exactly 37.5 for this row. That's the entire idea — everything from here on is nuance about what happens when the data gets messier.

The Full Algorithm, Step by Step

1 Pick a row with a missing value in some feature F.
2 Compute distance from this row to every other row, using only the features that are present in BOTH rows being compared (details in Nuance 1 below).
3 Sort by distance. Walk down the sorted list, SKIPPING any row that is also missing feature F (details in Nuance 2 below), until you've collected K valid neighbors.
4 Impute: average of F among those K neighbors (numeric), or majority vote (categorical — with real caveats, covered later).
5 Repeat independently for every missing cell in the dataset.
Notice: steps 2 and 3 are exactly where the real subtlety lives — and where most people's mental model of "just KNN, but for filling gaps" quietly breaks down. Let's go through both properly.
Nuance 1

What If OTHER Features Are Also Missing?

Real datasets rarely have just ONE column with gaps. Different rows are often missing DIFFERENT features. If Row A is missing Income and Row B is missing Age, how do you even compute a "distance" between them?

The fix: only use features present in BOTH rows being compared — then rescale the distance to compensate for using fewer coordinates. This is sklearn's nan_euclidean distance, and it's the actual formula KNNImputer uses.
distance(A,B) = √( (ntotal_features / npresent_features) × Σ (ai−bi)² over present features only )
The (n_total/n_present) term is the crucial part: without it, comparing two rows using only 1 shared feature would look artificially "closer" than comparing two rows using all 3 shared features, just because there are fewer terms being summed. Rescaling corrects that bias.

This is the entire point of the reweighting: a partial-feature comparison is allowed to genuinely win if the values that ARE shared are truly close, and it isn't unfairly penalized (or unfairly favored) just for having fewer coordinates.
Nuance 2

What If a Near Neighbor Is ALSO Missing This Feature?

Suppose Row A is missing Income, and its single closest neighbor by every OTHER feature is Row B — but Row B is also missing Income. Row B obviously can't donate a value it doesn't have.

The fix: skip it. A row that's also missing the target feature is completely excluded as a possible donor for that feature — no matter how close it is in distance. The algorithm just keeps walking further down the sorted-by-distance list until it finds K rows that actually HAVE a value to contribute.

The key lesson: "nearest by distance" and "nearest VALID donor" are two different rankings. A row can be the single closest match on every other feature and still contribute nothing, if it's missing exactly the one value you need.
Categorical features

How KNN Imputation Handles Categories

sklearn's KNNImputer is built for numbers. A column like City (Chennai/Mumbai/Delhi) has to be converted to numbers FIRST — typically with ordinal encoding (Chennai=0, Mumbai=1, Delhi=2, ...).

This is where a real, easy-to-miss problem shows up.

The Fractional-Category Problem

RowIncomeCity
058Chennai (0)
132Chennai (0)
260Mumbai (1)
390Mumbai (1)
488Mumbai (1)
5 (query)59? missing

Row 5's Income (59) sits almost exactly between Row 0 (58, Chennai) and Row 2 (60, Mumbai) — both at distance 1, a genuine tie for nearest.

Impute City_encoded = (0 + 1) / 2 = 0.5
0.5 is not a valid category. It's neither Chennai nor Mumbai — it's the arithmetic average of two category CODES, which was never a meaningful operation to begin with. Verified directly: sklearn's KNNImputer genuinely returns 0.5 here, silently, with no warning.

Two Ways to Fix It

Fix 1 — Round to the nearest valid category code

Take the raw KNNImputer output (0.5) and round it to the nearest integer, then map back to the category name.

Even this has a hidden nuance at an exact tie. Python's built-in round(0.5) uses "round half to even" (banker's rounding) and returns 0 (Chennai); the more familiar "round half up" convention returns 1 (Mumbai). Verified directly — these two, both reasonable-sounding rounding rules, disagree on this exact row. Rounding doesn't cleanly solve a genuine tie; it just moves the ambiguity into "which rounding convention did you pick."

Fix 2 — Majority vote among the K nearest neighbors' actual categories (don't average codes at all)

Instead of averaging 0 and 1 to get 0.5, just count: how many of the K nearest neighbors are Chennai, how many are Mumbai, and take the majority — exactly like KNN classification.

On THIS exact row, majority vote is also tied — 1 Chennai vote, 1 Mumbai vote (K=2, one neighbor of each). Switching strategies doesn't erase a genuine tie in the underlying data; it just avoids inventing a fake 0.5 category to paper over it.
The real fix for the tie itself: exactly the same lesson as KNN classification ties — prefer an odd K, or set an explicit tie-break rule (e.g. fall back to the single nearest neighbor's category). Category-averaging and its rounding fallback are really just symptoms; the underlying fix is the same one you already know from classification.

Wrapping up

Is This Used in Practice?

Yes, but selectively — genuinely common for small-to-medium tabular data with scattered missingness that plausibly correlates with other features (exactly the "new customer, no bill yet" kind of pattern real data has).

AlternativeWhy teams reach for it instead
Mean/median/mode imputationMuch cheaper; good enough when missing rate is low and the feature isn't critical
Tree models (XGBoost, LightGBM)Handle missing values natively — skip imputation entirely
MICE / IterativeImputerScales better than KNN imputation at very large n, since KNN imputation re-runs a distance search per missing value
The honest verdict: KNN Imputation is a genuinely reasonable, explainable choice for small/medium data with a plausible "similar rows should have similar values" story — which is exactly why it's still taught and still shows up in real pipelines, just not as the universal default.

Summary

ConceptOne-line takeaway
Core ideaFill a missing value with the average (or majority) of similar rows' values for that same feature
Basic algorithmDistance → sort → take K nearest → average (numeric) or vote (categorical)
Nuance 1: other features also missingUse only features shared by both rows; rescale distance by (total/present) to keep comparisons fair
Nuance 2: neighbor missing the target featureSkip it entirely as a donor, no matter how close — keep walking down the ranking until K valid donors are found
Categorical featuresMust be encoded to numbers first; naive averaging can produce invalid fractional category codes
Fixing categorical imputationRound (careful: rounding conventions can disagree at exact ties) or use majority vote (can also tie) — the real fix is the same odd-K/tie-break rule from KNN classification
Used in practice?Yes, for small/medium data with plausible row-similarity — not the universal default at scale
The whole topic in one sentence: KNN Imputation is "find similar rows, borrow their value" — and every nuance here (masked distances, skipped donors, fractional categories) exists because real data is rarely missing just one clean column at a time.
