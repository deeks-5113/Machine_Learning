The Core Confusion

One Subtree At a Time, Not One Leaf

You never remove leaves individually. The operation is always: pick ONE internal node, and turn its ENTIRE subtree — however many leaves it has — into a single leaf, all at once, in one move.

Two separate leaves: leaf 5 and leaf 6
Node 4 itself IS the leaf now — predicts one class for all 131 samples
Nothing was removed "one leaf at a time." You didn't first delete leaf 5, then separately decide about leaf 6. The WHOLE subtree below node 4 — both leaves, in one move — got replaced by exactly one leaf.

Where "−1" Literally Comes From

Not a clever formula choice — just counting, before and after, from the exact picture above:

Before collapsing:   2 leaves existed (leaf 5, leaf 6)
After collapsing:   1 leaf exists (node 4 itself, now a leaf)

Leaves eliminated  =  2 − 1  =  1
|Tt| is "how many leaves the subtree had BEFORE." The result of collapsing ANYTHING is always EXACTLY 1 leaf, no matter how many leaves you started with. So "leaves eliminated" is always (leaves before) minus 1 — not because 1 is special, but because collapsing always lands you at exactly one leaf, regardless of the starting count.

Same Counting, A Bigger Subtree

Watch the exact same logic hold for a much bigger subtree — node 0, the ENTIRE tree (4 leaves: 2, 3, 5, 6):

Leaves 2, 3, 5, 6 — all four, currently separate
All 4 gone — node 0 itself is now the only leaf
Leaves eliminated  =  4 − 1  =  3
If a subtree had 10 leaves, collapsing it would eliminate 9. The "−1" is not "remove one leaf" — it's "however many leaves you had, minus the one leaf you always end up with." Same rule, node 4 (2→1, eliminates 1) or node 0 (4→1, eliminates 3) — just plain subtraction, applied to whatever the actual leaf count happens to be.
The Full Algorithm, Drawn

Round 1 — Three Candidates, One Winner

Real tree, real class counts (breast cancer dataset). Every internal node is evaluated as a CANDIDATE — "what would alphat be if I collapsed THIS one?" — but nothing is collapsed yet. All three numbers get computed first.

Every leaf now shows its FULL class breakdown — this is what gets added together below, not just the "wrong" count in isolation.

Exactly how "wrong if collapsed" is calculated — for every candidate

"Collapsing" a node means: combine (add up) the class counts of every leaf underneath it, then check which class wins the combined majority. Whichever count is now the MINORITY becomes the new "wrong" count — those are the samples that would get misclassified if this node stopped splitting and just predicted one class for everyone.

node 4 collapses leaves 5 + 6 together:
class0: 0 (leaf 5) + 125 (leaf 6) = 125
class1: 3 (leaf 5) + 3 (leaf 6) = 6
Combined: 125 class0 vs 6 class1 → majority = class0 (125 > 6)
The MINORITY count becomes "wrong" → wrong-if-collapsed = 6
node 1 collapses leaves 2 + 3 together:
class0: 4 (leaf 2) + 19 (leaf 3) = 23
class1: 237 (leaf 2) + 7 (leaf 3) = 244
Combined: 23 class0 vs 244 class1 → majority = class1 (244 > 23)
The MINORITY count becomes "wrong" → wrong-if-collapsed = 23
node 0 collapses ALL FOUR leaves (2, 3, 5, 6) together:
class0: 4 + 19 + 0 + 125 = 148
class1: 237 + 7 + 3 + 3 = 250
Combined: 148 class0 vs 250 class1 → majority = class1 (250 > 148)
The MINORITY count becomes "wrong" → wrong-if-collapsed = 148
This is the SAME logic every single time: add up the raw class counts from every leaf under that node, find the new majority, and whatever's left over (the minority) is how many samples would be misclassified. No shortcuts, no separate formula — just addition, then one comparison.
CandidateWrong if collapsedWrong as subtreeLeaves before → afteralpha_t
node 0 (whole tree)1484+7+0+3=144 → 1(148−14)/(4−1) = 44.67
node 1234+7=112 → 1(23−11)/(2−1) = 12.0
node 4 ★ winner60+3=32 → 1(6−3)/(2−1) = 3.0
"Wrong as subtree" is a different, simpler addition — just add each leaf's OWN wrong count directly (no majority/minority check needed, since each leaf already made its own separate prediction). "Wrong if collapsed" is the one that needs the combine-then-find-new-majority step shown above, because collapsing forces ALL those samples to share one single new prediction.

Round 3 — Down To the Root

Only node 0 is left as an internal node. There's nothing to compare anymore — whatever alpha_t it has, it's automatically the "smallest" by default (the only candidate).

Both remaining leaves are themselves already-collapsed subtrees — their history doesn't matter, they're just leaves now.

Recomputing "wrong if collapsed" one final time

node 0 collapses LEAF 1 + LEAF 4 together (both already-collapsed leaves):
class0: 23 (leaf 1) + 125 (leaf 4) = 148
class1: 244 (leaf 1) + 6 (leaf 4) = 250
Combined: 148 class0 vs 250 class1 → majority = class1 (250 > 148)
wrong-if-collapsed = 148  (still the same 398 total samples, same answer as every round — only the grouping changed, never the underlying data)
wrong-as-subtree = wrong(leaf 1) + wrong(leaf 4) = 23 + 6 = 29

alpha_t = (148 − 29) / (2 − 1) = 119.0
Collapsing node 0 produces the trivial single-leaf tree — the root, predicting class1 for every one of the 398 training samples (since class1=250 is always the majority, no matter how the tree is grouped). No internal nodes remain. The algorithm stops here.
Same Idea, Regression

Now the Same Picture, for Regression

Identical mechanics — only "wrong count" becomes "SSE" (sum of squared errors from the mean). Real tree, real target values (diabetes dataset — predicting disease progression), node 4's subtree collapsing exactly like before.

Two leaves, each with its OWN tailored mean prediction
One mean (205.53) forced onto BOTH groups — fits neither well
SSE eliminated by keeping the split = 667,269.37 − (469,969.09 + 63,134.64) = 667,269.37 − 533,103.73 = 134,165.64 extra SSE if collapsed

Leaves eliminated = 2 − 1 = 1

alpha_t = 134,165.64 / 1 = 134,165.64
Same "−1" logic, same reason: 2 leaves existed, collapsing always produces exactly 1, so exactly 1 leaf gets eliminated here too. Only the numerator changed shape — extra SSE instead of extra wrong-predictions — because "error" now means something different.

Regression Round 1 — Three Candidates, One Winner

Same tree shape as the classification example (3 internal nodes: 0, 1, 4), same procedure — compute ALL candidates first, collapse only the smallest.

Same procedure as classification — all 3 candidates computed, only the smallest actually collapsed.

Exactly how "SSE if collapsed" is calculated — for every candidate

"Collapsing" a node means: pool ALL the raw target values from every leaf underneath it into one group, compute ONE new shared mean for that pooled group, then re-measure the squared error of every one of those pooled values against that single new mean. This is a completely fresh SSE calculation, not a sum of the old leaf SSEs.

node 4 pools leaf 5 (101 values) + leaf 6 (25 values) = 126 raw values together:
new shared mean = sum of all 126 values ÷ 126 = 205.53
SSE-if-collapsed = ∑ (each of the 126 values − 205.53)² = 667,269.37
node 1 pools leaf 2 (138 values) + leaf 3 (45 values) = 183 raw values together:
new shared mean = sum of all 183 values ÷ 183 = 118.36
SSE-if-collapsed = ∑ (each of the 183 values − 118.36)² = 665,445.91
This new mean is NEVER just the average of the two old leaf means (e.g. NOT (189.30+271.12)/2) — it's the mean of the raw, pooled, individual values, which correctly weights by how many samples came from each leaf. That's why it must be recomputed from scratch rather than combined arithmetically from the two existing leaf means.

node 1665,445.91530,615.552 → 1134,830.37

How This Becomes Code

Multiple Alphas Per Round — Which One Gets Stored?

Look back at Round 1 of either tree above: THREE candidate alphas were computed (one per internal node), but only ONE number — the smallest — actually changed anything or got recorded as a "breakpoint." This is exactly what cost_complexity_pruning_path() does internally, and it's worth being explicit about the computed-vs-stored distinction.

RoundCandidates COMPUTED (all internal nodes)Value actually STORED in ccp_alphas
1node 0: 44.67, node 1: 12.0, node 4: 3.03.0 (the minimum — node 4's)
2node 0: 65.5, node 1: 12.012.0 (the minimum — node 1's)
3node 0: 119.0 (only one left)119.0 (the only candidate, wins by default)
Every round computes MULTIPLE candidate numbers — one per internal node still standing — but stores exactly ONE per round: the minimum. Over 3 rounds, that's 3+2+1=6 numbers computed in total, but only 3 get returned to you (plus the starting 0 for the untouched full tree) — sklearn discards the "losing" candidates each round; they don't appear anywhere in the output array. This is the array you actually see:

path.ccp_alphas = [ 0,   3.0,   12.0,   119.0 ]
One entry per ROUND, not per candidate. The array length always equals (number of internal nodes in the fully grown tree) + 1 — one breakpoint per collapse, plus the starting alpha=0 for the untouched tree.

What this looks like as actual code

tree = DecisionTreeClassifier(max_depth=2, random_state=42).fit(Xtr, ytr)
path = tree.cost_complexity_pruning_path(Xtr, ytr)

# path.ccp_alphas  ==  [0, 3.0, 12.0, 119.0]     (the STORED, one-per-round values)
# path.impurities   ==  the total error R(T) of the tree AT each of those breakpoints
#
# internally, sklearn ran exactly the 3 rounds you just watched above:
# round 1: compute {node0:44.67, node1:12.0, node4:3.0} -> keep only min (3.0), discard 44.67 and 12.0
# round 2: compute {node0:65.5,  node1:12.0}             -> keep only min (12.0), discard 65.5
# round 3: compute {node0:119.0}                          -> only one candidate, keep it

How ccp_alpha=a actually PRUNES the tree when you call .fit()

Passing a specific alpha to a fresh estimator doesn't run some separate pruning function — it walks the exact round sequence above and STOPS as soon as the next round's breakpoint would exceed your chosen alpha.

ccp_alpha you passRounds appliedResulting tree
0.0None — stop before round 1 even starts (0 < 3.0)T0, full tree, 7 nodes
5.0Round 1 only (3.0 ≤ 5.0, but 12.0 > 5.0 — stop before round 2)T1, 5 nodes
50.0Rounds 1 and 2 (3.0 ≤ 50, 12.0 ≤ 50, but 119.0 > 50 — stop)T2, 3 nodes
200.0All 3 rounds (3.0, 12.0, and 119.0 are all ≤ 200)T3, 1 node (trivial leaf)
This is precisely why testing every value IN ccp_alphas (and nothing in between) is sufficient — any alpha strictly between two consecutive breakpoints applies the exact same set of rounds and therefore produces the IDENTICAL tree. Testing alpha=30 gives you exactly T2, same as alpha=50 — there's nothing new to discover between 12.0 and 119.0.

The full tuning loop, now fully explained end to end

path = full_tree.cost_complexity_pruning_path(Xtr, ytr)
candidates = path.ccp_alphas[:-1]   # drop the very last one -- collapses EVERYTHING to 1 leaf, rarely useful

best_alpha, best_score = 0.0, -1
for a in candidates:
    # each loop iteration = grow a FRESH tree, then walk rounds up to this specific alpha
    m = DecisionTreeClassifier(random_state=42, ccp_alpha=a).fit(Xtr, ytr)
    score = m.score(Xval, yval)          # evaluate THIS specific round's tree on held-out data
    if score > best_score:
        best_score, best_alpha = score, a

# best_alpha now identifies exactly ONE tree from the sequence T0...Tk --
# whichever round's tree scored best on validation, not on training data
Confirming your exact question: yes — for EACH candidate alpha (each stored breakpoint), a fresh tree is fit and scored on validation data, exactly like tuning any other hyperparameter. The only thing that makes ccp_alpha different from max_depth is where the candidate LIST comes from: here, it's the exact, finite, data-derived set of round-breakpoints traced out above — not a grid you guessed yourself.
After The Sequence Is Built

Once You Have T0...T3, How Do You Validate?

Everything above built the FULL sequence of trees (T0 through the trivial single-leaf tree) and their exact breakpoint alphas. That sequence is a MENU, not an answer — pruning itself never tells you which tree to actually deploy. That decision needs held-out data, exactly like tuning any other hyperparameter.

One honest wrinkle worth flagging directly: the round-by-round demo above was fit on the FULL 398-row training set, to keep the numbers clean for the derivation. Properly validating means carving out part of that training data as a validation set FIRST — which means the tree itself grows on fewer rows, and the resulting alpha breakpoints genuinely change. This is not a contradiction; it's the exact same "small data change → different tree" instability the whole course started from.

Step 1 — split properly, THEN regenerate the path

from sklearn.model_selection import train_test_split
from sklearn.tree import DecisionTreeClassifier

# train_full (398 rows) -> split further into train (298) + val (100)
X_train, X_val, y_train, y_val = train_test_split(
    X_train_full, y_train_full, test_size=0.25, random_state=42, stratify=y_train_full
)

# regenerate the candidate path from TRAIN ONLY -- val must never influence this
base = DecisionTreeClassifier(max_depth=2, random_state=42).fit(X_train, y_train)
alphas = base.cost_complexity_pruning_path(X_train, y_train).ccp_alphas
Real executed output — genuinely different breakpoints than the full-data demo above
Train rows: 298   Val rows: 100   Test rows: 171

Candidate alphas (from this smaller X_train): [0, 0.02434, 0.04328, 0.3481]
Compare to the earlier sequence built on the full 398 rows: [0, 3.0, 12.0, 119.0]. Genuinely different numbers — fewer training rows changed the tree's own structure, which changed every downstream alpha. This is expected, not an error.

Step 2 — fit EACH candidate fresh, score on validation, never on training accuracy

results = []
for a in alphas:
    m = DecisionTreeClassifier(max_depth=2, ccp_alpha=a, random_state=42)
    m.fit(X_train, y_train)
    train_acc = m.score(X_train, y_train)
    val_acc   = m.score(X_val, y_val)
    results.append((a, m.get_n_leaves(), train_acc, val_acc))
Real executed output — every candidate in the sequence, fit and scored
alpha=0.00000  leaves=4  train_acc=0.9732  val_acc=0.9600

Watch training accuracy alone and you'd be misled toward always picking alpha=0 (0.9732, the highest) — exactly the overfitting trap this whole document has been building toward avoiding. Validation accuracy is what actually decides it, and here alpha=0 AND alpha=0.02434 tie at 0.9600 — both genuinely competitive, not a clear single winner.

Step 3 — pick the best, refit on train+val, evaluate ONCE on untouched test data

best_alpha = max(results, key=lambda r: r[3])[0]   # highest val_acc wins ties by picking the first (alpha=0 here)

final = DecisionTreeClassifier(max_depth=2, ccp_alpha=best_alpha, random_state=42)
final.fit(X_train_full, y_train_full)   # refit on ALL 398 rows (train+val combined), same alpha

test_acc = final.score(X_test, y_test)   # the ONE time test data gets touched
Real executed output

On this particular split, validation genuinely picked "no pruning" as best — a legitimate, honest outcome, not a failure of the method. Pruning doesn't ALWAYS help; the validation step is what tells you whether it does for YOUR specific data, rather than assuming it must.

The workflow, summarized

TRAIN+VAL+TEST split → generate path from TRAIN only → fit+score every candidate on VAL → pick best → refit on TRAIN+VAL → score ONCE on TEST
Never let test data influence which alpha you pick — that decision belongs to validation alone, exactly the same discipline as every other hyperparameter in this course. And never trust training accuracy to make this call — it will always prefer the least-pruned tree, which is precisely the tree most likely to be overfit.
