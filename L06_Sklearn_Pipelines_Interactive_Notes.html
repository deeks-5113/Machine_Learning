Step 1 · From raw to ready

The raw-data → model journey

A model like ŷ = w₀ + w₁x₁ + ... only understands clean numbers. Real data almost never arrives that way. Before any modelling, every dataset goes through the same checklist:

The checklist, in order

1 Missing values check — cars.isnull().sum(). Decide per column: drop the row, drop the column, or impute (mean/median/mode).
2 Duplicates check — cars.duplicated().sum(). Duplicate rows silently inflate a pattern's importance and can even leak between train/test if not removed first.
3 Data dictionary pass — read what every column actually means before touching it. In our dataset: car_ID is just a row number (dropped), symboling is an insurance risk rating from -2 (safest) to +3 (riskiest) — genuinely ordered, so it's an OrdinalEncoder candidate, not a plain number to feed in directly.
4 Univariate analysis — look at one column at a time. For categorical columns, value counts (cars['aspiration'].value_counts()); for numeric columns, a histogram with sns.histplot(cars['price'], kde=True) to see the shape (skewed? multi-modal? outliers?).
5 Bivariate analysis — look at pairs of columns. sns.pairplot(cars_numeric) scatters every numeric column against every other — a near-straight-line scatter between two features is an early collinearity warning; between a feature and the target, it's a good predictive signal.
6 Correlation heatmap — sns.heatmap(cars_numeric.corr(), annot=True). From today's board: curbweight and enginesize both correlate ~0.84–0.87 with price — strong candidates — while carwidth correlates 0.87 with carlength, a collinearity flag between two features to keep in mind for Ridge/Lasso.
7 Cleaning — e.g. CarName arrives as messy free text ("alfa-romero giulia", "vw dasher", "toyouta corona"). We extract just the brand (car_company) via string split or regex, then fix misspellings (vw/vokswagen → volkswagen, toyouta → toyota, Nissan → nissan) before it ever reaches an encoder — an encoder has no way to know "vw" and "volkswagen" mean the same brand.
None of this is optional busywork — an encoder or scaler fit on dirty, duplicated, or mis-typed data faithfully learns the mess right along with the signal.
Step 2 · Encoding

One-Hot Encoding — for categories with no order

Models only understand numbers, but many columns are text categories: fueltype is "gas" or "diesel", carbody is "sedan", "hatchback", "wagon"... There's no natural ranking here — "hatchback" isn't "more" or "less" than "sedan". One-Hot Encoding's answer: create one new 0/1 column per category.

Worked example

Take doornumber, with values two/four/two/four across 4 rows:

rowdoornumber
0two
1four
2two
3four

becomes:

rowdoornumber_twodoornumber_four
010
101
210
301
Every row gets exactly one "1" — the column matching its category — and 0 everywhere else. No numeric ordering is implied between "two" and "four" anymore; the model just sees two independent yes/no signals.

The dummy-variable trap — why we drop one column

If a column has only 2 categories (like doornumber), doornumber_four is entirely predictable from doornumber_two (it's always the opposite) — this is perfect multicollinearity, one column is a linear function of the other. That's why the real pipeline code uses OneHotEncoder(drop='first', ...) — drop one category's column entirely; its information is still fully recoverable (all-zeros across the remaining columns = "it was the dropped category").

from sklearn.preprocessing import OneHotEncoder OneHotEncoder(drop='first', sparse_output=False, handle_unknown='ignore') # handle_unknown='ignore' -> if the test set has a brand-new category never seen # in training (e.g. a new car brand), it just encodes as all-zeros instead of crashing

Ordinal Encoding — for categories with a genuine order

Some categorical columns aren't really "categories" at all — they're numbers in disguise, with a real, meaningful rank. symboling (insurance risk: -2 → +3) and cylindernumber ("two", "four", "six", "eight"...) both have a genuine order: fewer cylinders always means fewer cylinders, safer always means safer. One-Hot would throw away that order — Ordinal Encoding preserves it by mapping each category to a single number reflecting its rank.

Worked example

cylindernumberencoded rank
two0
three1
four2
five3
six4
eight5
twelve6
from sklearn.preprocessing import OrdinalEncoder OE_categories_list = [ [-2, -1, 0, 1, 2, 3], # symboling: safest -> riskiest ['two','three','four','five','six','eight','twelve'] # fewer -> more cylinders ] OrdinalEncoder(categories=OE_categories_list)
Critical detail: you must pass the category order explicitly via categories=. Left to its defaults, OrdinalEncoder just sorts alphabetically — which would rank "eight" before "five" (alphabetical) instead of after (numerical) — silently teaching the model a completely wrong order.

One-Hot vs. Ordinal — the decision rule

question to askif yes →
Does the category have a genuine, meaningful rank?Ordinal Encoding
Are the categories just distinct labels with no order?One-Hot Encoding
Using Ordinal on an un-ordered column (e.g. encoding carbody as sedan=0, wagon=1, hatchback=2...) invents a fake numeric distance the model will wrongly trust — it would imply "hatchback" is "twice as much" as "wagon" in some sense, which is meaningless. Always match the encoder to whether real order exists.
⭐ Optional — mentioned for now, covered fully in a future class

What if a feature has hundreds of categories?

Our car_company column alone has 20+ brands — One-Hot would create 20+ new columns for that feature alone. Imagine a real-world "zip code" or "product SKU" column with 10,000+ unique values: One-Hot would explode into 10,000 columns, mostly zeros, and often overfits badly. Two techniques address this — Frequency Encoding (replace each category with how often it appears) and Target Encoding (replace each category with the average target value for that category, done carefully to avoid leakage). We'll cover both in detail, with worked examples, in a future class — for now, just know the problem exists and has a name: high-cardinality categorical features.

Step 3 · Scaling

Why scaling is needed at all

Look at two real columns from this dataset: enginesize ranges roughly 60–330, while compressionratio ranges roughly 7–23. Both matter for predicting price. So what goes wrong if we feed them in raw, unscaled?

The concrete problem

Imagine Ridge regression with its penalty λΣw². Suppose enginesize genuinely needs a small coefficient (say w≈0.5) to have a sensible effect on price, because its raw values are already large (100s). Meanwhile compressionratio needs a much larger coefficient (say w≈50) to have any comparable effect, because its raw values are small (single/double digits). Ridge's penalty λΣw² squares every weight equally — it will punish compressionratio's w=50 far more harshly than enginesize's w=0.5, purely because of the units the data happened to arrive in, not because compressionratio is actually 100× less important.
This is the core problem: regularization penalizes the numeric size of a weight, but a weight's size is partly an artifact of what units/scale its feature happens to be measured in. A feature measured in millimeters gets a naturally tiny coefficient; the same feature measured in kilometers would need a coefficient a million times larger for the identical real-world effect. Without scaling, Ridge/Lasso would unfairly punish whichever features happen to be measured in small units.
Same issue hits gradient descent directly: with wildly different feature scales, the loss surface becomes a long, thin, elongated bowl instead of a nice round one — gradient descent zig-zags slowly down the narrow direction instead of taking a direct path, needing far more iterations to converge. Distance-based methods (KNN, K-Means, SVM) are affected even more directly: Euclidean distance is dominated entirely by whichever feature has the largest raw numeric range, regardless of its actual importance.

Standard Scaler — Z-score normalization

The formula

x_scaled = (x − μ) / σ
μ = mean of the column, σ = standard deviation of the column.
After scaling: the transformed column always has mean 0 and standard deviation 1 — it tells you "how many standard deviations away from average is this value," a unit-free, directly comparable number regardless of the original feature's units.

fit vs. transform — the train/test discipline, with numbers

Say the training column horsepower = [100, 120, 140, 160, 180]. Mean μ=140, std σ≈28.28 (computed only from these 5 training values).

1 .fit(X_train) — computes and stores μ=140, σ=28.28 from training data only. No data is transformed yet.
2 .transform(X_train) — applies (x−140)/28.28 to each training value: 100→−1.41, 120→−0.71, 140→0, 160→0.71, 180→1.41.
3 .transform(X_test) — suppose the test set has horsepower=200. We reuse the same stored μ=140, σ=28.28 from training: (200−140)/28.28 = 2.12.
Notice test value 2.12 is outside the ±1.41 range the training data occupied — and that's completely fine and expected. What would be wrong is recomputing a fresh mean/std from the test set itself — that's data leakage: it lets information about the test set's distribution quietly influence preprocessing, giving an overly optimistic, unrealistic sense of how the model will perform on truly new data.
from sklearn.preprocessing import StandardScaler scaler = StandardScaler() scaler.fit(X_train) # learns mean & std from TRAIN only X_train_scaled = scaler.transform(X_train) X_test_scaled = scaler.transform(X_test) # reuses train's mean & std -- never refit # shortcut for the training step only: # X_train_scaled = scaler.fit_transform(X_train)

Min-Max Scaler — squeeze into a fixed range

The formula

x_scaled = (x − min) / (max − min)
Result always lands in [0, 1] for the training data itself (test data can spill slightly outside if it has more extreme values).
Worked example: wheelbase training values [86.6, 95.7, 99.4, 102.4, 120.9] → min=86.6, max=120.9, range=34.3. Value 99.4 scales to (99.4−86.6)/34.3 = 0.373. A future test value of 130 (higher than any training max!) would scale to (130−86.6)/34.3 = 1.27 — beyond 1, but the scaler doesn't clip it; it stays mathematically consistent with the stored train min/max.

Max-Abs Scaler — preserve sign, scale by magnitude only

The formula

x_scaled = x / max(|x|)
Result always lands in [−1, 1]. Zero always stays exactly zero (this is the key difference from Min-Max — Max-Abs is "zero-centered" in the sense that it never shifts zero away from zero).
Worked example: peakrpm training values [4150, 5000, 5500, 6000]. max(|x|)=6000. So 4150→0.692, 5000→0.833, 5500→0.917, 6000→1.0. If a column had negative values too, e.g. [−10000, 5000, 10000], max(|x|)=10000, giving [−1, 0.5, 1] — negatives stay negative, positives stay positive, only magnitude is rescaled.

Which scaler, when? — the decision table

scaleruse whensensitive to outliers?
StandardScalerDefault choice for most linear models (Ridge/Lasso/Linear Regression), features are roughly bell-shaped, or the model assumes/benefits from Gaussian-ish inputsYes — one huge outlier drags the mean and inflates σ, compressing everything else toward 0
MinMaxScalerNeural networks (many activation functions expect bounded input), image pixel data, or when you specifically need a bounded [0,1] rangeVery yes — a single outlier as the max/min stretches the entire scale, crushing all other values into a tiny sub-range
MaxAbsScalerSparse data (lots of zeros — e.g. one-hot encoded or text/TF-IDF features), since it never shifts zero and won't destroy sparsityYes, similar to MinMax, but at least preserves zero and sign
Rule of thumb for this specific class's model: our pipeline uses StandardScaler on the numeric columns feeding into Ridge — because Ridge/Lasso's penalty term compares coefficients directly against each other, and Standard Scaling puts every feature on the same "number of standard deviations" footing, which is exactly the comparison basis regularization needs.
⭐ Optional deep-dive

Robust Scaler — when outliers are the whole problem

The formula

x_scaled = (x − median) / IQR
IQR (Interquartile Range) = Q3 (75th percentile) − Q1 (25th percentile).
Why this resists outliers where the others don't: mean and standard deviation (used by StandardScaler) are both dragged around heavily by extreme values — a single outlier of 10,000 in a column of mostly 10–50 values massively distorts both. Median and IQR completely ignore the tails — the median doesn't care how extreme the largest value is, only what's in the middle, and IQR only looks at the middle 50% of the data, entirely excluding the top and bottom 25% where outliers live.

Worked example — same column, two scalers, one outlier added

Column: [10, 12, 14, 16, 18, 500] (that last value is a data-entry error/outlier).

scalerwhat happens
StandardScalermean≈95, std≈198 (both wildly dragged by 500) → the five real, normal values (10-18) all get squashed into a tiny range near −0.43, barely distinguishable from each other
RobustScalermedian=15, IQR = Q3(16.5)−Q1(11.5) = 5 → the five normal values scale to roughly (10-15)/5=−1 through (18-15)/5=0.6, staying nicely spread out and interpretable; only 500 itself becomes a huge, clearly-flagged outlier value (≈97), rather than distorting everything else
Use RobustScaler when your EDA (the univariate histograms from Step 1!) shows real, meaningful outliers you can't simply drop — e.g. genuine luxury cars in a dataset of economy cars, not data-entry errors. It keeps the bulk of your data well-spread and informative instead of letting a handful of extreme rows compress everything else into a narrow band.
from sklearn.preprocessing import RobustScaler scaler = RobustScaler() # same .fit / .transform discipline as every other scaler

Does everything need the same scale?

This is the question that trips almost everyone up at least once — let's settle it completely.

"If features are on different scales, is evaluation even valid?"

Yes, it's still completely valid — as long as you're consistent. R², MSE, and every other evaluation metric are computed on the model's final numeric predictions vs. actual target values — they don't care what internal scale the features were on to get there. What actually breaks is not evaluation validity, but two other specific things:

what breaks without scalingwhy
Regularization fairness (Ridge/Lasso)penalizes larger-magnitude weights more, and a feature's weight magnitude is partly just a units artifact (see the earlier section)
Gradient descent's convergence speedelongated, skewed loss surface → slow zig-zag convergence, more iterations needed
Distance-based methods (KNN, K-Means, SVM)Euclidean distance gets dominated by whichever feature has the largest raw range
Plain OLS Linear Regression with no regularization, evaluated by R² alone, is actually mathematically scale-invariant — you'd get the identical R² whether or not you scaled the inputs, because OLS just rescales the coefficients to compensate. Scaling becomes essential the moment any of these three things enter the picture: regularization, gradient-descent-based optimization, or distance-based computation.

"Should every feature use the same scaling method?"

Not necessarily, but almost always yes in practice, and here's how to actually decide:

1 Look at each numeric column's distribution (back to univariate EDA!). Roughly symmetric, no wild outliers → StandardScaler is fine.
2 A specific column has known, legitimate outliers you want to keep → RobustScaler for that column specifically.
3 You're feeding into a neural network that expects bounded [0,1] inputs → MinMaxScaler across the board, for architecture reasons, not a per-feature decision.
Mixing scalers across different feature groups (as in today's mechanics demo) is technically possible via ColumnTransformer — and there are legitimate cases for it (e.g. one group of features has outliers, another doesn't) — but it adds complexity and makes coefficients harder to compare directly in a linear model. For our actual Ridge model today, we deliberately used one consistent StandardScaler across all numeric columns — simpler, and directly supports fair regularization comparison across every coefficient.

"How do I know it actually worked?"

After fitting any scaler on your training data, sanity-check it directly:

X_train_scaled.mean() # should be ~0 for StandardScaler X_train_scaled.std() # should be ~1 for StandardScaler X_train_scaled.min(), X_train_scaled.max() # should be ~0, ~1 for MinMaxScaler
If these numbers don't come out as expected, the most common cause is fitting the scaler after the split was done incorrectly, or fitting on the wrong subset of columns — always re-check which exact DataFrame/columns actually went into .fit().
Step 4 · Assembling it into one object

ColumnTransformer — different transforms, different columns, one object

By now we need: OneHot on some columns, Ordinal on others, StandardScaler on the numeric ones — all applied to different subsets of the same DataFrame, then glued back together side by side. Doing this by hand (slice → transform → concat) is exactly the kind of manual bookkeeping that quietly breaks the moment you cross-validate or deploy. ColumnTransformer solves this once, declaratively.

The shape of it

ColumnTransformer(transformers=[ ('name1', transformer1, [list_of_columns_1]), ('name2', transformer2, [list_of_columns_2]), ... ], remainder='drop' | 'passthrough')
1 Each tuple = (a label you choose, a transformer instance, the list of columns it applies to).
2 All listed transformers run in parallel on their own column subset, and results are concatenated side by side.
3 remainder='drop' throws away any column not explicitly listed; remainder='passthrough' keeps unlisted columns unchanged and appends them.
4 .set_output(transform='pandas') (sklearn ≥1.2) returns a readable DataFrame with real column names, instead of a bare numpy array.

Real code from today's dataset — encoding half

OE_categories_list = [ [-2,-1,0,1,2,3], # symboling ['two','three','four','five','six','eight','twelve'] # cylindernumber ] encoding_demo = ColumnTransformer( transformers=[ ('ordinal', OrdinalEncoder(categories=OE_categories_list), ['symboling','cylindernumber']), ('onehot', OneHotEncoder(sparse_output=False, handle_unknown='ignore'), ['fueltype','aspiration','doornumber','carbody','drivewheel', 'enginelocation','enginetype','fuelsystem','car_company']), ], remainder='drop' ).set_output(transform='pandas')
Why bother with this instead of column-by-column pandas code? Because ColumnTransformer is itself a proper scikit-learn transformer — it has .fit()/.transform() — so it can be dropped straight into a Pipeline and cross-validated correctly (fit only on training folds, applied to validation folds) — something manual pandas code can't safely do without you personally rewriting the fit/transform split every single time.

Pipeline vs. FeatureUnion — chaining vs. combining

These solve two genuinely different problems and are very easy to mix up.

Pipeline — sequence

Runs steps one after another — each step's output feeds directly into the next step's input.

Step A

Step B

A common mistake: Pipeline(steps=[('encode', encoder), ('scale', scaler)]) would try to run the scaler on the already-encoded output — scaling one-hot 0/1 columns is usually pointless, and if encoder and scaler were meant for different original columns, this breaks entirely.

FeatureUnion — parallel

Runs multiple transformers in parallel on the same original input, and glues their outputs side by side into one wider table.

Encoder (A)
Scaler (B)
↘
↙

This is what we actually want here: encode the categorical columns and scale the numeric columns, both starting from the same raw cars DataFrame, then combined side by side — that's exactly parallel, not sequential.

Code: both, side by side

# Pipeline: sequential, output of step 1 -> input of step 2 Pipeline(steps=[('preprocess', preprocessor), ('model', Ridge(alpha=10))]) # FeatureUnion: parallel, both fed the SAME original input, results concatenated FeatureUnion(transformer_list=[ ('encoder', encoding_demo), ('scaler', scaling_demo), ]).set_output(transform='pandas')
In practice, for our actual model, we don't even need a separate FeatureUnion — a single ColumnTransformer already runs its listed transformers in parallel on column subsets of the same input and concatenates them, which is the FeatureUnion behavior we need, built in. FeatureUnion becomes genuinely necessary when combining two entirely different pipelines (e.g. one whole preprocessing pipeline plus a separate feature-engineering pipeline) rather than simple column-subset transformers.

fit_transform vs. transform — and why modeling only calls .fit / .score

The three methods every transformer has

methodwhat it doesuse on...
fit(X)Learns parameters from X (mean/std, min/max, categories seen, etc.) and stores them internally. Does not transform anything.Never call alone in practice — usually via fit_transform
fit_transform(X)Learns parameters from X and immediately applies the transform to X, in one call. A convenience shortcut for fit(X) then transform(X).X_train only
transform(X)Applies the already-learned parameters (from a prior fit) to new data X. Learns nothing new.X_test (and validation folds)
Calling fit_transform(X_test) instead of transform(X_test) is one of the most common, most silent bugs in ML code — it re-learns mean/std/min/max/categories from the test set itself, meaning the test set's own distribution leaks into preprocessing. The model still "runs," scores can even look fine or better, but the reported performance no longer honestly reflects how it would do on genuinely new, unseen data.

So why, once wrapped in a Pipeline, do we only ever call .fit() and .score()?

This is the elegant part — the Pipeline object hides the fit_transform/transform distinction from you entirely, and gets it right automatically:

ridge_pipeline = Pipeline(steps=[ ('preprocess', preprocessor), ('model', Ridge(alpha=10)) ]) ridge_pipeline.fit(X_train, y_train) # internally this does: # preprocessor.fit_transform(X_train) -> learns + transforms training data # Ridge().fit(transformed_X_train, y_train) -> fits the model on the transformed output train_score = ridge_pipeline.score(X_train, y_train) test_score = ridge_pipeline.score(X_test, y_test) # internally .score(X_test, y_test) does: # preprocessor.transform(X_test) -> REUSES the already-learned train statistics, no relearning # Ridge().predict(transformed_X_test) -> then compares predictions to y_test for R^2
This is the entire point of wrapping everything in one Pipeline: calling .fit() once on the whole pipeline correctly fits the preprocessor with fit_transform on training data and fits the model on that transformed output, in the right order, automatically. Calling .score() or .predict() afterward automatically uses .transform() (never refitting) on whatever new data you pass in. You never manually have to remember "was this fit_transform or transform" again — the Pipeline object enforces the correct discipline structurally, which is exactly why it's the safe default for real projects, and why cross-validation tools like GridSearchCV(estimator=ridge_pipeline, param_grid=..., cv=5) can wrap the entire thing and repeat this fit/transform discipline correctly, fresh, inside every single fold.

When to use — and not use — a pipeline

Use a Pipeline when...

  • You have any preprocessing step at all (encoding, scaling, imputing) before a model
  • You plan to cross-validate or grid-search — Pipeline is the only safe way to avoid leakage across folds automatically
  • You're deploying the model — a saved Pipeline bundles preprocessing + model into one shippable object, so production code doesn't need to separately remember every preprocessing step
  • Multiple team members / notebooks need to reproduce the exact same preprocessing consistently

Skip it (or simplify) when...

  • You're doing quick, one-off, exploratory EDA plots — the ceremony isn't worth it for a histogram
  • Your data already arrives fully numeric, clean, and pre-scaled from an upstream source you control
  • You genuinely need to inspect intermediate transformed data interactively at every step (though pipeline.named_steps['preprocess'].transform(X) can still get you this without abandoning the pipeline)
A pipeline is not "more correct" in some abstract sense — it's a discipline-enforcement tool. If you're careful and consistent by hand, you could avoid leakage without one. In practice, almost nobody stays that careful across dozens of experiments and re-runs, which is exactly why Pipeline is treated as the default in real ML codebases.
⭐ Optional deep-dive

Custom Transformers — when sklearn doesn't have the exact step you need

Sometimes the transformation you need isn't a scaler or encoder at all — it's a bit of custom logic (like our earlier CarName → car_company extraction). To make custom logic pipeline-compatible (so it gets the same safe fit/transform discipline as everything else), sklearn gives you two options.

Option 1 — FunctionTransformer (quick, stateless logic)

For transformations that need no "learning" from training data (no stored mean/std/categories) — e.g. a log transform to fix skewed data.

from sklearn.preprocessing import FunctionTransformer import numpy as np # price is right-skewed (see the histogram from Step 1) -> log-transform to compress the long tail log_transformer = FunctionTransformer(np.log1p, inverse_func=np.expm1) X_train_log = log_transformer.fit_transform(X_train[['enginesize']]) X_test_log = log_transformer.transform(X_test[['enginesize']]) # np.log1p(x) = log(1+x) -- safely handles zero values, unlike plain log(x)

Option 2 — a full custom class (when you need to "learn" something from training data)

Build your own transformer by inheriting sklearn's base classes, giving it real fit/transform methods:

from sklearn.base import BaseEstimator, TransformerMixin class CarNameExtractor(BaseEstimator, TransformerMixin): """Extracts brand from 'CarName' and fixes known misspellings.""" def __init__(self): self.fixes = { 'vw': 'volkswagen', 'vokswagen': 'volkswagen', 'porcshce': 'porsche', 'toyouta': 'toyota', 'Nissan': 'nissan', 'maxda': 'mazda', } def fit(self, X, y=None): return self # nothing to learn from data -- just needs to satisfy the transformer interface def transform(self, X): X = X.copy() brand = X['CarName'].str.split(' ').str[0].str.lower() X['car_company'] = brand.replace(self.fixes) return X.drop(columns=['CarName']) # now it behaves exactly like any built-in sklearn transformer: extractor = CarNameExtractor() cars_cleaned = extractor.fit_transform(cars)
Because it inherits TransformerMixin, this class automatically gets a working .fit_transform() (built from your .fit() + .transform()), and because it inherits BaseEstimator, it plays nicely with GridSearchCV's parameter introspection. That means it can slot directly into a ColumnTransformer or Pipeline step exactly like StandardScaler or OneHotEncoder — sklearn has no idea (and doesn't care) that you wrote it yourself.

End-to-end: before → custom transformer → after

stageCarName / car_company
Before (raw)"toyouta corona", "vw dasher", "porcshce panamera"
After .transform()"toyota", "volkswagen", "porsche"
Slotting it into the full pipeline: Pipeline(steps=[('clean', CarNameExtractor()), ('preprocess', preprocessor), ('model', Ridge())]) — cleaning now happens as a proper, leak-safe, cross-validation-compatible pipeline step, instead of a one-off script cell run manually before everything else.
