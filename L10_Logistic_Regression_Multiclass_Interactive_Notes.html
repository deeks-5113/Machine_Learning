The business problem

Telecom Customer Churn — properly explained

A telecom company wants to know, for each customer, whether they are likely to churn (leave for a competitor) or stay. Acquiring a new customer costs 5-25× more than retaining an existing one — so flagging at-risk customers before they leave is directly worth money.

The features, grouped by what they tell you

Who they areState, Account Length, Area CodeTenure, rough location
Plan choicesIntl Plan, VMail Plan, VMail MessageWhich optional services they've opted into
Actual usageDay/Eve/Night/Intl Mins, Calls, ChargeHow much they talk, when, what it costs them
How they've been treatedCustServ CallsHow often they've had a problem needing support
Target: Churn — a single column, 0 or 1. Two possible outcomes — exactly the shape of problem logistic regression is built for.

Why logistic regression, specifically — the validation checklist

QuestionAnswer here
Is the target categorical?Yes — Churn is 0/1
Do we need a probability, not just a label?Yes — the business wants to rank customers by churn risk, not just get a blunt yes/no
Do we need interpretable coefficients?Yes — the business wants to know why customers churn
Is data size reasonable?~5,700 rows — plenty for a stable fit

Stratified Sampling — a fully worked example

What it is, and how it differs from a plain random split

A normal train_test_split shuffles rows randomly — it does not guarantee each resulting split has the same class ratio as the original data. Stratified sampling fixes this: every split (train, validation, test) preserves the same class proportions as the full dataset.

Why we need it here — the actual verified numbers

splitrowsClass 0 (No Churn)Class 1 (Churn)
Full data5,7000.5000.500
Train3,4200.5000.500
Validation1,1400.5000.500
Test1,1400.5000.500
Every single split lands at exactly 0.500/0.500 — a perfect miniature of the full dataset, every time. That's stratification doing its job. Try removing stratify=y and re-running — on a smaller split especially, these numbers will drift apart purely from random luck.

The code, step by step

1 Split off the test set first (20%), stratified on y: train_test_split(X, y, test_size=0.20, stratify=y)
2 Split the remaining 80% into train (75% of it = 60% of total) and validation (25% of it = 20% of total), stratified again on the remaining labels: train_test_split(X_tr_cv, y_tr_cv, test_size=0.25, stratify=y_tr_cv)
3 Verify: print value_counts(normalize=True) on all four (full, train, val, test) and confirm they match — never skip this check.

Precision, Recall, F1, and Support — computed by hand

Churn row (the class we usually care most about)

Precision_Churn = TP/(TP+FP) = 413/(413+113) = 413/526 = 0.785
Recall_Churn = TP/(TP+FN) = 413/(413+157) = 413/570 = 0.725
F1_Churn = 2×(0.785×0.725)/(0.785+0.725) = 0.754
Support_Churn = TP+FN = 413+157 = 570  (total ACTUAL churners in the test set)

No Churn row

Precision_NoChurn = TN/(TN+FN) = 457/(457+157) = 457/614 = 0.744
Recall_NoChurn = TN/(TN+FP) = 457/(457+113) = 457/570 = 0.802
F1_NoChurn = 2×(0.744×0.802)/(0.744+0.802) = 0.772
Support_NoChurn = TN+FP = 457+113 = 570
Support is simply a row-count — how many actual examples of that class exist in the test set. It's not a computed rate like the other three; it's just there so you can judge how much evidence each row's precision/recall is even based on. A "recall=1.00" on a support of 3 means much less than the same number on a support of 570.

Macro & Weighted — the actual calculation

Macro average — simple, unweighted average across classes

Macro-Precision = (0.744 + 0.785)/2 = 0.765 ≈ 0.76
Macro-Recall = (0.802 + 0.725)/2 = 0.763 ≈ 0.76
Macro-F1 = (0.772 + 0.754)/2 = 0.763 ≈ 0.76

Weighted average — each class's score weighted by its support

Weighted-F1 = (570/1140)×0.772 + (570/1140)×0.754 = 0.5×0.772 + 0.5×0.754 = 0.763 ≈ 0.76
Macro and Weighted come out identical here — not a coincidence, but a direct consequence of the classes being perfectly balanced (570 = 570). The weighting factor is 0.5 for both classes, so weighted average collapses to the same formula as macro average. This will NOT happen on imbalanced data — Class 09's Iris multiclass example, and the worked example later in this class, show macro and weighted genuinely diverging once class sizes differ.
Scaling up to 3+ classes

Multiclass Confusion Matrix → P/R/F1, fully end to end

Binary confusion matrices are 2×2. With K classes, it becomes K×K. Let's take a genuinely small, hand-computable example — 3 classes, 8 points (4 of class 0, 2 of class 1, 2 of class 2) — and compute absolutely everything from the raw matrix up.

The confusion matrix (rows = actual, columns = predicted)

      pred: 0   1   2
actual 0: [ 4,  0,  0 ]
actual 1: [ 1,  1,  0 ]
actual 2: [ 0,  0,  2 ]
Reading it: class 0's 4 examples were all predicted correctly. Class 1 has only 2 examples — one predicted correctly, one wrongly predicted as class 0. Class 2's 2 examples were both correct.

Per-class Precision, Recall, F1 — computed directly from the matrix

For each class k, treat it as "class k vs. everything else" using just that row/column of the matrix:

041 (the class-1 point)04/5=0.8004/4=1.0000.889
1101 (predicted as 0 instead)1/1=1.0001/2=0.5000.667
22002/2=1.0002/2=1.0001.000
Precision_0 = TP_0/(TP_0+FP_0) = 4/(4+1) = 0.8 — column 0 has 5 total predictions (4 correct class-0's + 1 misclassified class-1 point wrongly landing here), so precision asks "of those 5 'class 0' predictions, how many were really class 0?"

Now Macro and Weighted — from these same three rows

Macro-F1 = (0.889+0.667+1.000)/3 = 0.852
Weighted-F1 = (4/8)(0.889) + (2/8)(0.667) + (2/8)(1.000) = 0.861
Macro (0.852) and weighted (0.861) genuinely differ here because class 1 is both the worst-performing class AND the smallest class — exactly the situation worth watching for. (There's also a third averaging option, micro — covered separately in Class 09 if you want the full derivation; skipping it here to keep focus.)
From probability to decision

predict_proba() — what it actually returns

model.predict(X) gives you the final 0/1 label, already thresholded at 0.5 internally. model.predict_proba(X) gives you the raw probability the decision was based on — for binary classification, one column per class, always summing to 1 per row.

y_test_prob = final_model.predict_proba(X_test)[:, 1]  # probability of class 1 (Churn) specifically
Why [:, 1]: column 0 is P(No Churn), column 1 is P(Churn) — they're redundant (P(Churn)=1−P(No Churn)), so for binary problems we usually just keep the "positive class" column and work with that single number directly.

The binarize() function, explained properly

binarize() does exactly one thing: take an array of continuous values and turn each one into 0 or 1, based on a threshold you specify — the exact mechanical step that .predict() performs automatically at 0.5 under the hood, now exposed so you can use any threshold you choose.

from sklearn.preprocessing import binarize y_pred_thresh_03 = binarize(y_test_prob.reshape(-1, 1), threshold=0.3).ravel()
1 y_test_prob is a 1D array of probabilities — binarize() expects a 2D array, hence .reshape(-1, 1) first.
2 Every value ≥ 0.3 becomes 1, everything below becomes 0.
3 .ravel() flattens the result back to a plain 1D array, matching the shape classification_report expects.
What actually happened when we tried threshold=0.3 on the real churn data: No Churn's precision/recall/F1 all collapsed to 0.00. This is a real, honest result — it means essentially every test row's predicted Churn-probability already sat above 0.3, so lowering the bar that far reclassified almost everyone as "Churn," leaving nothing predicted as "No Churn" at all. A concrete, slightly extreme illustration of exactly why 0.5 is a default, not a law — but also a caution that swinging the threshold too far in one direction can break a class entirely, not just shift the trade-off gently.
Multiclass internals, in full mathematical depth

Recap: fitting the line, before we extend it

For binary classification we fit one line (one weight vector w, one bias b) and pushed its score z=w·x+b through a single sigmoid. For K classes, the natural next question: do we need K entirely separate ideas, or can we extend this one cleanly? The answer is both approaches genuinely exist — and understanding exactly how each one works is the rest of this section.

What softmax is, and why we reach for it

Instead of one weight vector, fit one weight vector per class — a full weight matrix W (features × classes) plus one bias per class. For any input x, compute K raw scores at once:

zk = wk · x + bk   for every class k = 0, 1, ..., K−1

Then convert all K scores together into a valid probability distribution using softmax:

P(class=k | x) = ezk / Σj ezj

That Σj is just a compact way of writing "add up every class's exponential." Written out fully for K=3 classes (j = 0, 1, 2), with no shorthand at all:

P(class=k | x) = ezk / ( ez0 + ez1 + ez2 )
Every output is positive (exponentials are always positive) and they sum to exactly 1 by construction — not by a separate normalizing step bolted on afterward. This is the whole reason we reach for softmax: it's the direct, principled generalization of "squash a score into a valid probability," extended from one score to K scores that are all competing against each other simultaneously.
Sanity check — softmax collapses to sigmoid when K=2: P(class=1) = ez1/(ez0+ez1). Divide top and bottom by ez1: = 1/(1+ez0−z1) = σ(z1−z0) — our familiar sigmoid, applied to the difference of the two classes' scores. Softmax isn't a new idea bolted onto logistic regression — it is the sigmoid, generalized.

The weight matrix — softmax vs. OvR, side by side

Softmax (Multinomial) — ONE joint matrix

W has shape (n_features, K classes)
ALL columns trained together, in one optimization

Every class's weight column is fit with full knowledge of every other class's column — increasing confidence in class 0 for a point directly competes against classes 1, 2 during training, because they all share one softmax denominator.

One-vs-Rest (OvR) — K SEPARATE matrices

K independent weight vectors, each shape (n_features,)
Each trained in its OWN, unrelated optimization

The "class 0 vs rest" classifier has zero information about the "class 1 vs rest" classifier's weights — they're fit completely independently, as if the other classes didn't exist.

Full worked example — z → p → loss, line by line

Setup

2 features, 3 classes. One input row x = [2, 1]. Weight matrix W (2 features × 3 classes) and bias b already fitted to some values:

class 0class 1class 2
weight for feature 1 (w1,k)0.30.90.1
weight for feature 2 (w2,k)0.20.40.0
bias (bk)0.20.30.1

Step 1 — forward pass: compute zk = wk·x + bk, one class at a time

class 0 z0 = (0.3×2) + (0.2×1) + 0.2  =  0.6 + 0.2 + 0.2  =  1.0
class 1 z1 = (0.9×2) + (0.4×1) + 0.3  =  1.8 + 0.4 + 0.3  =  2.5
class 2 z2 = (0.1×2) + (0.0×1) + 0.1  =  0.2 + 0.0 + 0.1  =  0.3
z = [1.0, 2.5, 0.3]

Step 2 — softmax: turn the 3 raw scores into probabilities

2a Exponentiate each score: e1.0=2.718,  e2.5=12.182,  e0.3=1.350
2b Sum them (the softmax denominator): 2.718 + 12.182 + 1.350 = 16.250
2c Divide each exponential by that sum: p0=2.718/16.250=0.1673,  p1=12.182/16.250=0.7497,  p2=1.350/16.250=0.0831
p = [0.1673, 0.7497, 0.0831]   (sums to 1.0000 ✓)

Step 3 — loss, for a few different possible true classes

Same p vector every time — only the true class changes. This is the cleanest way to see that loss is always just −log(probability the model gave the correct answer):

if true class were…one-hot yloss = −log(ptrue)reading
class 0[1, 0, 0]−log(0.1673) = 1.788the model gave the true class low probability — a fairly costly mistake
class 1 (our actual example)[0, 1, 0]−log(0.7497) = 0.288the model's top pick WAS the true class — small loss
class 2[0, 0, 1]−log(0.0831) = 2.488the model gave the true class its lowest probability — the worst case here

And two more extreme cases, on a fresh made-up p vector, to see the full range:

scenariop vectortrue classloss
confident & correct[0.02, 0.95, 0.03]1−log(0.95) = 0.051
confident & WRONG[0.90, 0.05, 0.05]1−log(0.05) = 2.996
Same pattern as binary log loss, just extended to K classes: being confidently right costs almost nothing, being confidently wrong costs a lot — unbounded, in fact, as ptrue→0.

Multiclass Log Loss — derived, not just stated

The general multiclass cross-entropy formula, for one sample:

L = − Σk yk · log(pk)

Written out fully for K=3 (no shorthand):

L = −[ y0·log(p0) + y1·log(p1) + y2·log(p2) ]

Here yk is one-hot — exactly 1 for the true class, 0 for every other class. Watch what this does to the sum, using our true-class-1 example (y=[0,1,0]):

1 y0·log(p0) = 0×log(0.1673) = 0 — vanishes, regardless of what p0 is
2 y1·log(p1) = 1×log(0.7497) = log(0.7497) — the only term that survives
3 y2·log(p2) = 0×log(0.0831) = 0 — vanishes too
L = −[0 + log(0.7497) + 0] = −log(ptrue class)
This is the exact same "masking trick" from binary log loss (where the (1−y) term killed off whichever piece didn't apply) — just extended from 2 terms to K terms. Multiclass log loss isn't a new formula to memorize; it's the same idea, generalized.

The gradient & weight update — the result, and how to use it

The result — remarkably simple

∂L/∂zk = pk − yk    — for EVERY class k, simultaneously

Same "predicted minus actual" residual shape as binary logistic regression — now one such residual per class, all at once. Verified numerically (finite-difference check) on our worked example: analytic gradient [0.1673, −0.2503, 0.0831] matched the numerical gradient exactly.

⭐ Optional — the calculus derivation, skip freely

If you want to see exactly where pk−yk comes from, rather than just trust it: it falls out of the chain rule applied across softmax and the log, in exactly the same style as the binary derivation from Class 06 — three linked pieces (∂L/∂pk, ∂pk/∂zk, and the cross-terms ∂pj/∂zk for j≠k), which all cancel down to the same clean subtraction once multiplied through. The full step-by-step algebra mirrors the binary "Piece 1 × Piece 2" collapse from Class 08 almost exactly — only with more terms to track. Happy to write out the full multiclass version line by line if you want it as a separate optional appendix.

The actual weight update, with real numbers

wk := wk − η · (pk − yk) · x   (one update per class, using the SAME gradient formula)

Using our example (x=[2,1], p=[0.1673, 0.7497, 0.0831], true class=1, η=0.5):

classgradient (pk−yk)update = −η×grad×xnew weight column
00.1673[−0.167, −0.084][0.133, 0.116]
1 (true class)−0.2503[+0.250, +0.125][1.150, 0.525]
20.0831[−0.083, −0.042][0.017, −0.042]
The TRUE class's weight column moves toward x (positive update); the other two classes' columns move away from it (negative update) — pulling the model to prefer class 1 for this input. Re-running the forward pass with these updated weights: loss drops from 0.2881 → 0.0994 — verified directly, the update genuinely improves the prediction.

OvR vs. Softmax — the same numbers, side by side

Same input x=[2,1] — but OvR trains 3 completely unrelated classifiers

These 3 weight vectors were never trained together — each one only ever saw its own "this class vs. everyone else" binary problem:

classifierraw score zkits OWN sigmoid σ(zk)
"class 0 vs rest"0.750.679
"class 1 vs rest"2.300.909
"class 2 vs rest"0.100.525
Sum of the three sigmoids = 0.679+0.909+0.525 = 2.113  ← NOT 1!
Each classifier had no idea the other two exist — there was never any reason for their outputs to sum to anything meaningful.

Making them sum to 1 — two genuinely different roads to the same-shaped answer

OvR (after-the-fact fix)Softmax (built in from the start)
class 00.679 / 2.113 = 0.3210.167
class 10.909 / 2.113 = 0.4300.750
class 20.525 / 2.113 = 0.2480.083
sum1.0001.000
Same shape (3 numbers, summing to 1) — genuinely different numbers. OvR's version is simple division on scores that were never designed to compete against each other. Softmax's version is what the model was optimized to produce from its very first training step.

How the best class is chosen — in both cases

Both use argmax — and both agree on the winner here (class 1) — but on different underlying quantities:

OvR Predicted class = argmax of the 3 raw, unnormalized sigmoid scores [0.679, 0.909, 0.525]. Dividing every number by the same positive constant (2.113) never changes which one is largest — so normalizing afterward doesn't change the prediction at all, only the reported confidence numbers.
Softmax Predicted class = argmax of p = [0.167, 0.750, 0.083] — which is also just argmax of the raw z scores directly, since the exponential function never changes the ranking order either.
